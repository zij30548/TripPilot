## 1. 本轮目标与停止点

第3步完成了独立旅行引擎，但原聊天接口尚未使用它。本轮将候选接到已有`assistant-turns`／`dialogue-action`与原浏览器控制器，让一次消息按现有工作区归属和持久版本进入，结果以程序文字或待确认操作返回。主导航仍是纯聊天、资料检索与执行核查三页；不恢复旅行卡片，不新增排程器、费用计算器或存档格式。

## 2. 请求、提议、确认与执行

### 2.1 显式接入，不偷偷切换现有服务

后端增加可信配置`ASSISTANT_RUNTIME=echomind_travel_v1`，默认仍为`legacy`。新路径只接受现有`dialogue-v2`，不新增聊天协议，不接受浏览器参数选引擎；缺少选装依赖时503，其他surface明确422，不自动回退旧引擎。普通应用启动不导入选装核心。示例只写占位／说明，没有修改现有`.env`、3110／8804或云端。

入口为[api/assistant.py](../backend/api/assistant.py)，适配器为[echomind_core/integration.py](../backend/echomind_core/integration.py)：

1. 读取服务端owner下的会话、地点副本和明确偏好，严格校验并捕获独立快照；过期地点不冒充当前地点，更不从名称猜POI。
2. 复用`ChatStore.begin_turn`和`AssistantStore.begin`持久预记，再执行原旅行候选的直接工具路径。owner、operation、session及单调版本共同绑定，工具前和最终投影前再查当前状态。
3. 原生`tool_calls`→严格工具校验／执行→原生工具反馈。复用第3步的角色／Skill和桥接，不启动Embedding、Redis或Chroma，不自动进入融合分类或旅行并行。最多3模型／4工具／45秒、单次2048／累计6144最大输出预约不变。
4. 模型自由正文不作为业务答案；仅投影程序生成的需求草稿、固定说明或白名单动作。沿用原`dialogue-action`读回，浏览器再核验当前版本，按原控制器确认／执行。
5. `finish_turn`及任务finalize继续使用原CAS；提交结果不确定时只读回、不自动重发。提议回执可以为waiting；不能因为浏览器稍后完成保存，就倒写成服务端已经执行过保存。

本轮不改表、快照或存档格式，不复制排程／计费器。新路径仍有旧主流程中未使用的兼容注册构造，但不执行第二引擎，也没有第二模型请求作为回退。

### 2.2 需求确认为什么需要单独处理

原`begin_turn`会清除确认标志。若每次聊天都如此处理，已经确认的需求会在“看费用／搜索地点”等未改需求的消息后重新变成未确认。本轮在[memory/chat_storage.py](../backend/memory/chat_storage.py)增加内部`ConfirmationCarry`：只在事务内从真实已确认行捕获，绑定同owner、会话、operation、running revision和需求／来源／issues摘要。完成时再次检查CAS和前后内容，**完全未变才继承确认到新revision**。

它不是HTTP可提交的权限字段，也不是密码学签名或完整恢复凭据。新需求、来源／issues变化、取消、失败、旧回调和ABA均不能继承；旧runtime默认行为不变。模型整理的需求只写为**待确认草稿**，原确认接口仍需用户操作。浏览器在准备规划前也检查确认，拒绝时不会先清空／同步地点。

### 2.3 浏览器显示上下文不是事实来源

原浏览器掌握正式草案、费用、可选地点和预览。为解释“第二天／这个公园／地点1”等表达，将既有严格`DialogueSelectionContext`作为**独立、有界、不可信标签区**给候选：复制、重验、绑定请求；不放宽原Request.context，不让客户端自报状态变成执行依据。仍受16 KiB独立区、20 KiB角色包及48 KiB总请求限制，超限拒绝而不截断。最终读取和操作依然由当前浏览器控制器决定。

费用、时间、地点与正式结果不是模型生成；日期读取不会切地图，预览不替换正式草案，采用使用所见结果，保存使用原冻结快照和幂等标识。

## 5. 演示、原理与后续准入

### 3分钟受控演示（不是实时模型演示）

用本轮已有截图／只读收据：先展示未确认需求草稿→说明真实POI仍需独立主动搜索／地址确认→`04`查看实际程序排程及空日→`16`核对未知不当零→`18/19`对照取消与采用→`20`另存及历史→`17`说明回执只证明服务端部分、语义未评分。不得将合成“受控景点甲”称为真实高德地点；重启受控工具也不是新的付费验收授权。

**30～60秒口述**：这一步不是再写一套聊天Agent，而是把保留下来的EchoMind旅行候选接到项目已有的持久任务和领域控制器。模型只选白名单工具，程序返回事实；需求整理先是草稿，必须用户确认。我把确认继承绑定到事务里的同一操作和未变需求，解决聊天后确认丢失，又不让旧请求复活。费用、预览、采用、保存仍用同一套规则。真实MySQL和浏览器与受控模型／高德分开验，测试通过不代表模型已经理解对了，也不代表线上切换。

面试追问：

1. **只改千问地址为什么不够？** 原生工具历史、权限、额度、持久幂等和浏览器确认都需要适配；原结构不提供本项目的owner／版本权威。
2. **既然原框架有Agent，为什么还要CAS？** 每对象防重复不抗重启／跨进程；既有MySQL准入拒绝已用op，未知提交只读回，不能承诺外部exactly-once。
3. **怎样避免确认被聊天破坏或自动获得？** carry只从真实已确认行事务捕获；前后需求／来源／issues未变且同running CAS才继承，模型草稿不能自确认。
4. **费用为什么不由Agent算？** 原整数分和时间轴逐次计费已经是权威；模型只提出读取／编辑动作，未知与非法值由程序处理。
5. **评测页通过代表什么？** 只核预算和服务端收据；尝试不等计费，零占位耗时不是真实0秒，语义选材和浏览器最终状态须另验。原pytest退出缺陷也如实保留。
