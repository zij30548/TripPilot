# 旅行候选小型验收方案：先固定计划，再授权发送

**本轮只准备验收，真实模型、高德和其他外部业务API均0次。** 用户的“开始”承接零调用方案准备，不是新的付费授权。没有修改候选、提示、Schema、模型、数据库、环境文件、现有服务或网站；知识生成问答仍停用。

## 1. 要验证什么

验证现在的**协调者 direct-tools → 原生工具反馈 → 后端严格操作提议 → 浏览器原控制器 → 实际业务状态**，不再迁移框架或增加Agent。四个旅行角色已定义，但当前正式opt-in每轮没有前置融合分类，未传明确意图时由协调者选工具；自动专业并行关闭。本组不能证明四Agent协作、三路融合、向量检索、Judge或任意旅行问题都正确。

受控测试已经证明部分程序接线和安全边界；真实模型是否理解原话、选对工具、尊重否定和多轮修正，必须另验。反过来，HTTP200、模型输出流畅、服务端waiting回执也不证明浏览器完成了操作。

**本方案先隔离变量：未来使用真实千问＋明确标注的合成旅行输入／受控高德transport。** 不对真实高德、天气、公交、地图底图重新验收，计划高德物理发送为0。合成地点不得写成已从高德核实的真实POI。这可以先定位理解与执行问题；之后若要补真实地点联调，须独立固定输入及有界查询计划，不在本批偷偷增加调用。

### 前提分开，不能拿旧工作区凑成功

- `empty`：独立空会话，未确认需求、地点、草案和费用均为空。

- `formal`：另一独立会话，上海2026-11-01～02、2人、预算3000、步行；沿用[既有受控工具](../backend/tools/echomind_travel_controlled.py)的“受控住宿甲／受控景点甲／受控公园甲”。先通过原接口／控制器正常准备：明确确认需求、合成地点搜索／预览／确认、准备规划、候选及生成。首日有一个必去及一个可选，第二天空日；09:00～18:00、停留各60分钟、午餐关闭、各方向参考360秒、住宿往返。候选仅该公园，无替补。费用为必去门票`0`、可选门票空白、首日餐饮`100`、次日餐饮／住宿／其他空白。程序应算交通参考0、已填估算100、小计100；缺项不当零。

### 计数与异常不能混为一谈

`received`只表示HTTP正文完整收到，绝不是工具选择、事实或业务通过。HTTP200的非法结构／普通语义失败留给原校验及人工评分，不修补成成功；网络、计数、版本、超时／取消、非200、超限或未读完则保守暂停。

主审修复了“claim前被拒却可以继续下一题”的边界：request hook即使尚未产生attempt，仍持久pause；调用方吞掉异常、重启或重开Ledger也不能继续m02。已有在途请求可以追加收到／失败／取消的结果，但**暂停锁永不因此解除**，也不退款。重复取消先排空真实落盘线程；不在finally强行seal或覆盖原异常。
