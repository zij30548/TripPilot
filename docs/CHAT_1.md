## 用户路径与模型职责

1. 正常登录，进入简洁会话列表、消息区及输入区。读取列表不调用模型；新建按钮先打开空白本地编辑，第一次主动发送才持久创建会话。
2. 用户分几轮补充／纠正需求，每次主动发送最多一次模型请求。后端读取自己的历史与当前意向，客户端不能提交owner、system消息、工具或伪造的历史。
3. 模型只给严格的完整意向、修改字段对应的本轮原话引用、有限问题码；程序展示固定澄清和限制文案，不展示模型自由生成的旅游事实。
4. 卡片显示城市、首尾日期、人数、全程全部旅客预算、住宿名称线索、想去地点顺序、交通意向与补充偏好。当前必需项为城市、完整日期、人数、预算及住宿线索；想去地点可留空。确认只确认**需求意向**，不是Place、TripRequest或已经生成的行程。
5. 用户点击确认后记录当前版本；继续发消息立即使旧确认失效。语义歧义、范围／动作不支持、失败、取消或结果不确定时不能确认旧卡片。偏好可记录但明确尚未执行，不升级为长期记忆。

例如“带父母、别太赶”只保存为本次意向，不声称排程已满足。未核实的“灵隐寺／西湖附近”没有POI ID、坐标或归属；真正搜索和确认留到chat-2。当前六城／七日／单住宿及6个地点线索边界保持，不支持跨城、自动订票或自由执行。

**原文引用只证明这段文字来自本轮输入，不能证明模型理解正确。** 模型仍可能误解否定、指代、预算口径或相对日期；Schema和引文存在性不能替代真实语义评审。前端按普通文本渲染，不执行用户或模型提供的HTML／指令。

## 数据流和版本

```text
用户文本 + 会话ID + expected_revision + operation_id
  → 服务端身份/CSRF + 有界请求
  → 短事务预记turn，递增revision，清除旧确认
  → 读取绑定的服务端历史与意向，核对本轮仍running
  → 一次有界千问请求（实际发送处持久计数）
  → 严格结构/本轮引文/日期与金额等校验
  → 短事务再次核对owner、operation和revision
  → 提交提议与程序消息 → 用户主动确认
```

- 前端使用AbortController、单调请求代数及身份epoch；后端使用持久revision和唯一操作约束。二者职责不同，不能只比较城市／文本相等或时间戳。A→B→A、晚成功／错误／finally、旧取消和旧确认均不能覆盖新状态。
- 每份会话一个活动turn；数据库锁只覆盖本地短事务，绝不持锁等待模型。发送前登记后即占用本次操作，重启也不能重复发同一操作。创建会话的不确定重试只复用原创建ID，不顺带再次发模型。
- `begin_turn`完成、模型任务注册之前也可能取消；任务注册后再读持久状态，已取消则0发送。同进程取消会取消模型任务；跨进程／已发送情况不能保证供应商停止处理或计费，最终提交仍由持久版本拒绝旧结果。
- 进程中断后遗留running／uncertain不自动重发；用户先读取收据，可显式取消running。这里是防重放收据，不是chat-5的完整任务恢复。
- 确认和逻辑删除不调用模型。删除清空该会话的文本、意向、引文和展示标题，保留最小操作墓碑防旧事件重新发送；不是物理磁盘安全擦除，也不会改历史行程存档。未发送草稿、当前选中会话不持久化。
- 正常退出／换号清空前端临时内容，但已经存下的对话仍归原账号；不同账号读取ID返回404。没有生产免登录开关。

## 契约与资源边界

- `chat-session-v1`／`chat-list-v1`与`chat-intent-v1`，不改saved-trip-v1/v2/v3。严格额外字段、重复JSON键、非有限数、UUIDv4、列表和文本边界；模型必须显式给出全部9个意向字段，不用默认值修补缺字段。
- 用户单条1～2000字；服务端完整解析前16 KiB／5秒有界接收。每会话20次turn、最多40条消息；最多50个活动会话、累计200个含墓碑的会话，不以删除／重启恢复操作身份。
- 城市来自现有六城定义；日期按日历校验1～7天和闰日，日期字符串限定2000～2100年；人数1～100为本阶段有界输入。预算为正的普通十进制人民币文本，最多13位整数／2位小数并检查安全整数分，不做费用计算、报价或自动缩放。
- 地点／偏好文字每项≤120字，地点≤6、偏好≤8；修改引用≤9条，每条≤300字且字段唯一。“本轮修改依据”不是整张卡所有字段的来源索引。
- 沿用当前受支持Flash与北京官方配置；非思考、非流式、1024输出Token、整次20秒、响应≤32 KiB，内容解析沿用旧严格适配器，不放宽原AI接口。全部序列化请求含Schema／历史≤48 KiB；长对话可早于20轮触顶，明确`chat_context_limit`且不发送／不截断，需新建会话。前端等待上限25秒、响应读取≤384 KiB。
- 新turn路径在实际发送计数白名单中归`qwen_text`，失败／已发取消保守计入；计数失败不发送。重试模型、二次总结、隐式工具、搜索／天气／排程和自动保存均不存在。
- 新同源资源及5条严格UUID动态路径显式加入Next转发和发布产物校验；仍只用可信服务端origin，旧发布产物白名单仍可核验。没有任意路径／URL转发。日志只给操作ID、版本、请求模型、耗时及可取得用量，不记录对话、密钥或模型思维链。

## 存储与迁移：不自动动旧库

同一个已配置私有数据库增加`chat_conversations`／`chat_turns`，以`storage_metadata.chat_version=chat-storage-v1`声明完整扩展。原`identity-v1`／`private-mysql-v1`版本和所有原表校验不改；扩展有严格表／列／唯一键／外键验证，缺表、未知版本／字段或损坏内容失败关闭。MySQL仍是显式选型，无故障回退SQLite；旧库没有扩展时原身份／存档可用，聊天明确`chat_migration_required`，不启动时建表。

新增CLI从**已停写的私有副本**复制到全新隔离目标，保留账号、会话、原存档、全部额度attempt和原库外锚。原库不就地升级；MySQL使用独立空库、管理互斥锁和一致快照，DDL部分提交失败保留目标／新私密收据，不自动重跑。SQLite复制前后核对原文件哈希。回退演练只允许聊天表尚无任何记录的新副本；新写入后不得回旧库返额、丢消息或复活会话。

从backend目录运行帮助（安全、不执行迁移）：

```sh
.venv/bin/python -B -m tools.chat_storage --help
.venv/bin/python -B -m tools.chat_storage sqlite-copy --help
.venv/bin/python -B -m tools.chat_storage mysql-copy --help
```

SQLite复制需要`--source`、`--destination`、`--receipt`、`--confirm-source-stopped`。MySQL读取可信服务端源配置，目标仅从私密`TRIPPILOT_CHAT_COPY_TARGET_URL`取得，另必需`--anchor`／新`--receipt`／停写声明；目标仅允许随机`trippilot_chat_<32hex>`或独立测试库，不是生产切换入口。不将真实URL写进文档／命令参数；未迁移时先体验页面并如实显示存储未就绪，不靠假回复兜底。

**部署限制**：旧八表MySQL逻辑备份格式不能安全包含新对话，本轮显式拒绝带扩展的库，避免“备份成功”却漏数据。当前复制工具只用于无聊天或空聊天回退演练，不是已写入对话后的完整备份／恢复方案；生产切换前必须补齐并验收这一运维门槛。没有把新版本直接部署到用户服务器，原SQLite备份／MySQL旧版迁移语义保留。

## 面试怎么讲（只讲已做和实际限制）

### 30～60秒口述

> 我把旅行产品的默认入口从复杂表单工作台重构为聊天，但第一步没有直接做自主Agent。用户分几轮表达需求，后端保存原话和版本化意向，模型一次只提出字段及原文引用，程序校验并展示需求卡，用户确认后才记录确认状态。未核实地点不能变成真实POI，也不会自动查路线。前端用请求代数防晚响应，后端短事务预记操作，再按版本提交，取消和重启不允许同一操作重新发模型。我做了独立MySQL迁移演练、受控流程和浏览器验证；本轮没有真实模型额度，所以不把这些测试说成模型理解质量已通过，也没有把这一步叫Agent loop。

### 追问与回答依据

1. **为什么不把聊天历史直接当需求？** 原话会纠正、否定和含歧义；历史用于理解，独立意向快照用于校验，用户确认再单独版本化。看`schemas/chat.py`、`services/chat.py`及24条轨迹，当前还不是正式TripRequest。
2. **为什么前后端都要版本？** 前端代数阻止旧回调污染当前屏幕，服务端revision／唯一操作防跨标签和重启后的旧提交。看`chat-controller.ts`和`chat_storage.py`，取消登记间隙与ABA各有回归。
3. **如何防重复计费？** 每次操作ID持久登记，已用不能再发；实际HTTP发送还走原持久额度。取消不返额、不保证上游停费，结果不明先读收据。看API／metering测试；不宣称外部系统exactly-once。
4. **有JSON和原文引用就不会理解错了吗？** 不是。它们限制结构和出处，不能证明否定／指代或字段语义正确。需真实固定轨迹评审；当前仅离线和受控流程通过，模型语义待验。
5. **为什么还没做完整Agent或长期记忆？** 这一步先把多轮需求、权限和状态做可靠；工具／真实旅行闭环、loop、任务恢复和跨旅行偏好各有独立门槛。用户本次偏好在会话内保存，不等于已确认的长期画像。

亲自阅读与修改顺序：`schemas/chat.py` → `services/chat.py` → `api/chat.py` → `chat_storage.py` → 前端`chat.ts`／`chat-controller.ts`／聊天组件 → 对应测试。先用独立测试库与受控模型学会跑通取消／版本冲突，不用真实额度排障。
