# EchoMind完整方法的旅行领域适配：离线完整候选

更新：2026-10-24；开工基线`d31f258841ba8fa68a6d4a670760374c6f0d2dbf`。这是用户明确要求保留原方法、只换旅行角色／提示／工具／Skill后的第一轮完整候选实现，**不是原网站已切换、全部迁移已验收或真实效果改善报告**。

## 1. 本轮到底做了什么

旧HTTP候选把融合分类和执行分开、旅行并行关闭，不能把“原代码已复制”说成整条方法已运行。本轮新增`FullTravelCandidate`，用同一任务、同一provider和同一预算接通原算法。没有再写一个融合器、调度器、检索器或计费器。

```text
已绑定的工作区／操作／输入版本
  → 加载已验证模板（不自动生成）
  → 可选：Redis工作记忆＋Chroma相关历史＋MySQL明确偏好
  → 原LLM／Embedding／Pattern融合
  → 原结构化主辅路由＋旅行权重和权限
  → 单角色，或限定的行程＋费用独立只读协作
  → 原native tool_use反馈；必要时原改写／并行召回／去重／重排
  → 多角色时原Composer
  → 程序只投影实际工具结果、缺口或待执行提议
```

后端仍没有浏览器的正式草案／费用权威状态。行程和费用工具返回**待浏览器版本复核的读取提议**，`executed=false`；不是两个Agent已经读到并核算。Composer确实执行，但其自由正文不成为业务事实；程序保留真实工具结果。这是旅行安全边界，不是隐藏的第二套排程或金额计算。

**本轮真实千问／Embedding／高德／其他业务外部调用均0。** 用户表示测试总次数不设限，但单任务不能无限执行；这不是把暂停的旧台账解锁。本轮没有发送器、真实场景冻结、网站／环境／服务／云端切换。

## 2. 四个Agent怎么分工

每个角色沿用原`AgentProfile`，有mission、workflow、input/output contract、handoff、tool_scope、model、temperature和max_tokens。真实工具以本轮native定义和服务端handler为准，profile中的可选名称只是权限上限。

| 角色 | 负责什么 | 不能做什么 |
| --- | --- | --- |
| `travel_coordinator` | 理解原意、缺项澄清、整理需求、主辅分工、历史／偏好入口 | 不自造旅行事实，不直接采用、保存或认定偏好已满足 |
| `travel_planning` | 当前日期／规则、天气诉求、确定性排程与排除预览提议 | 不成为第二套排程器，不跳过真实地点确认或预览采用 |
| `travel_budget` | 读取已有费用结果、未知与非法项、明确费用填写提议 | 不把未知当零，不在后端复制整数分规则，不以便宜为由自动采用 |
| `travel_place_reference` | 地点搜索／预览／确认入口、带来源的资料检索 | 不把同名POI当照片认证，不把相关资料当已回答、免费或可入场保证 |

原`GENERAL/TECHNICAL/BILLING/ESCALATION`四枚举仍是内部兼容槽，公开职责已是上面四类；没有假装框架已改成任意角色插件。原CRITICAL标记也不代表已接通人工服务。

Monitor统计的是原Agent技术执行：native结束但没有有效工具结果时，原Agent可能先记技术success，完整候选随后仍会拒绝发布。它不是端到端业务成功率，更不能代替语义评测。两个专员同时降级到同一协调者也可能安全失败，不承诺所有组合请求都能完成。

当前12个旅行意图：需求、地点、行程、费用、天气、调整、存档、偏好、资料、澄清、问候、其他。原融合权重和投票代码、有限结构化实体、置信输出保留；融合分数不是校准后的正确率。只读并行目前仅保守准入“查看当前安排和费用”，不宣称通用多问分解、依赖DAG或自动跨域执行。修改／先后依赖／否定／第三领域请求不能靠关键词进入并行写操作。

## 3. 八份Skill和工具权限

新增目录`backend/skills/travel_domain_v2/`；原3份Skill和上游源码不变：

| Skill ID | 核心约束 |
| --- | --- |
| `travel_intake` | 原话、补充、否定、需求确认分开 |
| `place_discovery_confirmation` | 真实地点搜索、地址核对、预览不等于确认 |
| `schedule_constraints` | 复用既有规则，保留空日、部分安排和失败 |
| `budget_review` | 整数分、已知／未知／非法、预算限定 |
| `weather_material_grounding` | 来源、日期、馆区、实时缺口与资料提示 |
| `adjustment_adoption` | 预览不改正式方案，采用重查版本 |
| `archive_media_navigation` | 历史只读、媒体仅线索、主动入口 |
| `memory_and_failure_governance` | 明确同意、撤回、未知调用不重试、错误不伪成功 |

新包实际调用原Skill发现／解析／匹配算法。每个任务捕获一次内容及hash；任务中修改文件不改变已捕获规则，下次任务才读取。固定文件集、大小、属主／权限、软硬链接、特殊文件、加载时变化及截断都有拒绝测试。不新增长期运行的任意文件／URL插件入口。

`travel_capabilities.py`复用原38个动作、10组Schema，增加有限角色→具体action授权及效果元数据（read／external_read／proposal／confirmed_write）。不能只过滤group而放行同组所有操作；执行前重新校验，改消费端Schema也不能放宽handler。元数据的动作效果不代表后端已经执行：现有38动作仍由浏览器控制器确认／执行。

native工具数上限仍16。完整RAG模式显式替换重复的旧资料入口，不把所有工具堆给每个Agent；未注册的可选工具不会偷偷可用。并行专员及降级协调者都被缩到只读白名单；同一响应的多个native调用仍按旅行边界拒绝，两个Agent不是让单个模型随意多调。

`upstream/`和`SOURCE.json`没有改。`python -B tools/echomind_core_manifest.py`继续验证36文件／11namespace的来源重建。保留代码不等于所有行为原样放开：全局私密learn、无同意画像写入、任意工具／URL、未知结果重跑仍禁止。

### RAG和事实边界

可信调用方必须先确定已审核城市／馆区／可选日期，改写不能跳去其他馆。召回结果保留完整主题摘要、短摘录、来源链接、内容版本、发布日期／更新时间／实际获取日期和适用性；原文与整理摘要分开。没有新采集或修改语料。

原重排只给模型短候选预览，本轮没有偷偷改算法；这可能丢条件、造成选材偏差。最终显示完整单元只能证明程序未改正文，不能证明模型选对、答全或当前适用。没有检索结果、改写超限、来源异常或预算不足都明确失败，不扩查、不截断条件、不让模型补答案。知识库生成式问答仍停用。

新增`ReviewedVectorRecall`显式复用原`KnowledgeBase.add_documents/search`和Chroma，不拿BM25改名向量检索。可信调用方先主动`prepare()`导入当前审核馆区；单次最多32完整单元、原500字分块后最多10个不同Embedding输入，仍受原上传／模型／任务上限约束，不自动分批扩额。原分块不变，向量命中后按语料hash＋单元身份校验文档ID、版本、title、chunk和content，再投影回完整主题条件；未知／篡改项令整个任务失败，不被其他子查询成功掩盖。未准备先拒绝，不自动填充索引。该端口的实际Chroma／Embedding HTTP验证使用临时私有索引和合成向量，不是真实召回质量；当前持久重开／新请求索引就绪管理仍待正式生命周期接线。

工具单条结果仍32000字节，最终最多4条／96000字节；不通过新增档位放宽这些原边界。素材或资料过大明确失败，不能静默删掉来源或条件。

### 记忆和同意边界

- 工作记忆来源为捕获的MySQL历史，Redis只是缓存；Chroma相关历史经原接口读取。
- 当前明确同意的MySQL偏好每次操作前后重新核对；模型推断不能覆盖用户本轮要求。
- `maintain()`是显式维护，不是每轮悄悄调用。原压缩的暂存结果经源revision／digest CAS发布Redis摘要，不删除源消息；摘要可丢弃，不是权威状态。
- 原画像提取可显式执行，但输出仅为`model_inference / consent=false`待确认提议；自动情景写入也保留为未发布候选。原用户确认的情景存储仍可显式使用，不能假造同意。
- 当前聊天历史捕获上限有限，没有自动读取全部MySQL历史、自动维护长对话、跨会话迁移记忆或完整断点恢复。这些仍需可信业务接线和验收。

## 5. 测试无限轮，不等于一次任务无限调用

旧HTTP／旧冻结仍为3模型／4工具／45秒，原`TaskBudget`不变。新完整候选必须显式选`TravelTaskBudget`，所有角色及检索共用**原预留锁和计数方法**：

| 服务端档位 | 模型尝试（含Embedding） | 工具尝试 | 输出Token预留上限 | 整任务截止 |
| --- | ---: | ---: | ---: | ---: |
| single | 6 | 8 | 8192 | 60秒 |
| collaboration | 10 | 12 | 16384 | 90秒 |
| reference | 16 | 16 | 24576 | 90秒 |

单次输出仍≤2048、输入48000字节；原native Agent最多3轮反馈，不自动加轮／重试。分档由可信代码选，不接受模型／请求传限额。预留Token不是实际用量或人民币；工具外层和实际召回都占次数，缓存命中不等于又发请求。持久产品额度、任务额度、验收台账职责不同，不能靠创建子Agent获得新额度。

用户本轮说明测试可多轮开展；此处实现运行预算，**本轮没有消费新的真实测试额度**，未来先冻结输入／场景／参数和记录方式，再记录每次实际发送。旧3/21、9/12、媒体和知识问答台账仍保持原失败／暂停／耗尽状态，不迁移或重置。

## 6. 怎样运行、怎样验收

完整候选只有显式Python入口，不新增公开API或默认开关：

```python
# 示意：可信服务端组合，不能从HTTP body构造权限／scope。
package = TravelDomainPackage().capture()
bridge = TravelToolBridge(trusted_snapshot, authoritative_current, parallel_reads=True)
recognizer = TravelIntentRecognizer(owner_scoped_embedding)
candidate = FullTravelCandidate(bridge, recognizer, package=package,
    prepared=validated_templates, memory=explicit_memory_port,
    retrieval=bound_reviewed_retrieval, observation=process_observation)
gate = ExecutionGate(scope, current_scope, TravelTaskBudget(TravelBudgetTier.REFERENCE))
# 必须已有原持久owner/usage准入；candidate.run不替代MySQL turn/CAS。
result = await candidate.run(captured_request, gate, settings, metered_client)
```

模板必须是同owner／revision／24模板顺序、固定Embedding模型／1024维的严格附件；加载不请求模型。没有真实artifact时先失败`embedding_preparation_required`，不先发分类或记忆Embedding，也不以测试向量补生产。结构有效不认证向量的真实来源。

本轮受控组合已检查：实际native wire、融合后专业工具选择、两专员＋原Composer、原检索各阶段、完整来源、只读降级、不合格工具、版本晚响应、取消占额、一次操作不可重用；真临时Redis／Chroma下记忆context＋完整候选共用4次受控发送。旧HTTP／ASGI／持久准入与原路径另做回归，不把候选对象的一次性guard当分布式幂等。

检查命令与结果见[本轮进度](PROGRESS.md)：最终源码的EchoMind回归590项通过，原HTTP／动作／资料兼容70项通过；此前完整候选／向量／记忆组合32项为子集，均为受控机制而非语义成绩。没有前端改动，不伪造新Chrome／Webpack成绩；已有网站3110／8804、8000和MySQL服务未切换。

## 7. 当前缺口和下一步停止线

**本轮停在完整方法的旅行候选离线接通，不宣布当前网站已经全部使用它。** 剩余关键接线／验收：

1. 明确真实模板／知识向量准备的来源、预算和冻结记录；当前没有生产假向量或自动准备。
2. 为完整候选增加独立HTTP生命周期／配置准入，继续复用MySQL持久操作和CAS，按新档位核对前端超时、计数与trace容量。不能把它塞进旧3次协议后悄悄放宽。
3. 核对同一浏览器版本的两项读取执行与结果回执；当前服务端只证明提议，未证明用户得到了两个实际答案。
4. 接入明确的长历史供给／维护调度与记忆撤回测试；不把缓存、最终存档或用户画像当任务恢复。
5. 固定真实语义对照，单步方案为基线，分别评意图、路由／选材、条件／未知、实际动作结果、延迟和用量；不以“工具200”或更多Agent数量为收益证据。
6. Linux生命周期、长时资源、部署、安全、生产备份恢复仍独立待验；不操作云端。

这不是架构方法“全部已上线”的交付。上述缺口完成前，不自动切默认网站、恢复知识生成问答、接机酒交易或进入下一个产品功能。

30秒口述：我没有把旅行助手只改成几个不同prompt。保留EchoMind的融合识别、主辅路由、工具反馈、检索、记忆与监控算法，旅行差异放在角色契约和白名单里。测试会观察原方法是否真的被调用，并验证所有分支共享额度。模型只选择工具，不直接提交行程或编造金额；目前完整候选通过的是受控机制，还没切到默认网站或证明真实回答质量。

面试追问：

1. **为什么不用所有请求都并行？** 会增加成本和冲突；当前仅有限独立只读组合，依赖／修改等待确认，单步仍有对照基线。
2. **怎么证明不是只复制框架？** 测试spy原fusion、run_parallel、Composer、检索和MemoryManager；同时看实际native HTTP与程序结果，不只看类名。
3. **为什么多了预算？** 原3次无法承载融合2次再多角色／检索；独立档位显式设计、所有分支共享锁，旧协议不改。无限测试轮数不意味着单任务无限循环。
4. **RAG来源正确就能答对吗？** 不能。引用身份、相关性、子问覆盖、条件／例外和当前适用性分开；生成问答仍因旧质量问题停用。
5. **记忆和任务恢复一样吗？** 不一样。缓存摘要帮理解，MySQL确认信息是权威；外部结果未知不能盲重跑，完整浏览器任务恢复仍待实现。

**结论：原方法的受控组合及现有控制器回归通过，但完整候选尚不具备当前网站的端到端真实验收条件。** 下面四处接线缺口被实际契约／投影复现，不是模型回答质量失败，也不能用测试通过数量抵消。旧HTTP的3模型／4工具／45秒仍保持原边界；这不是宣布当前所有聊天操作都坏了。

### 9.2 可复现的接线阻塞

新增只读工具`tools/full_travel_readiness.py`及11项工具测试。它没有发送入口、不读取实际.env、不连接数据库／浏览器，也不启动服务。运行时调用当前Pydantic契约、原预算预留方法和当前动作投影；等待值由执行者明确读源码后输入，绑定源码SHA，标为`source-inspected-not-browser-tested`。

```sh
cd backend
# 使用已安装echomind选装依赖的环境，不运行live/付费验收脚本。
python -B -m tools.full_travel_readiness \
  --frontend-wait-ms 65000 --proxy-wait-ms 75000
```

当前预期退出码是**2／blocked**，不是成功：

1. `Settings.assistant_runtime`仍只有`legacy`、`echomind_travel_v1`；实际API准入导入的也是旧`AdmittedTravelTurn`。完整候选没有声明的HTTP接线。工具中的full-runtime名称只是拟名，不是新增开关；枚举校验本身不代替API执行证明。
2. 两个单独只读动作各自通过`project_action`，组合后报`dialogue_receipt_invalid`。仅循环调用两个旧执行器还会遇到其互斥锁，不能这样“修复”。须让整批读取共享一个捕获的本地草案／费用版本，再整体核对身份、操作和版本后显示。
3. 新档位真实内存**预约**6/8、10/12、16/16，在本探针的“仅聚合计数、无逐步事件”输入下，经旧`_trace_rows`显示为3/4；后两档也被`TaskView`上限拒绝。带事件的旧投影同样有8条容量限制，但本轮没有把这一例冒充实际完整任务trace。预约不是实际发送或成功用量；新接线须准确表达两者，不能删限额或用截断后的数证明低成本。
4. 读源码确认浏览器等待65秒、Next转发75秒，无法覆盖完整候选90秒档位。生产Nginx等待也须另审，不能只改某一层就称线上可用。本轮没有真实等90秒或浏览器超时实测。

此外，读取当前准备方式发现：24个旅行模板尚无真实获取附件；测试使用的合成向量不能投入实际聊天。原私有资源端口已存在，但完整HTTP尚无请求级打开／取消排空／关闭接线，知识向量也没有已审核的跨请求只读重开收据。它们是前置准备缺口，不是靠再问千问一次就能验证的问题。

**停止在功能验收检查与明确阻塞，不宣布完整网站可直接使用新框架。** 下一步优先同一旅行闭环的最小接线：①原持久准入＋请求资源工厂；②真实模板／索引显式准备与来源；③有限只读批次的快照绑定、执行与回执；④与预算相符的超时和准确计数。先通过受控全链，再冻结少量真实场景、实际请求与发送台账。用户同意测试不设总轮数，不意味着任务无上限、自动循环、绕过这次阻塞或复用旧额度；本轮没有真实模型语义分数。

面试口述：我按用户要完成的事情验收，而不是看类名或测试数量。原框架各方法能受控运行，但检查到浏览器只能接收一个动作，两个Agent的结果会在交接处失败；另外超时和计数也没同步。因此我做了零网络的可执行探针，把“已提出动作”和“用户确实拿到结果”分开，先阻断无效付费验收，再补接线。

可追问：如何证明原方法实际执行（spy＋native HTTP）？为什么Mock通过不是模型质量（选择由脚本给出）？为什么不直接扩大旧Schema（旧协议需兼容、原计数语义不同）？为什么暂停真实调用（确定性接线错误无需付费定位）？为什么先不切网站（候选、正式执行和用户状态必须一致）？
