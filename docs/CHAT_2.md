## 先用一句话说清楚

**chat-1帮用户说清“想去哪”；chat-2把名称核对成真实地点；chat-3才把这些地点排成行程。** 例如“想去拙政园”只是一段文字，不能直接当成带坐标的景点。

2026-10-21，开工基线`c9d7a02365bdd162b5038940640a363858352cfa`。用户本轮同意更新方案并开始离线开发，**真实模型与高德业务调用额度均为0**。本页同时记实施顺序与实际交付，未验证项不能因写入方案而变成已完成。chat-1真实多轮语义仍待验，chat-2的真实语义／上游验收也须另获授权；离线开发不等于绕过这个门槛。

## 1. 用户最终会怎样用

以下是目标交互例子，不是本轮真实模型或高德成功记录：

1. 进入自己的旅行对话，点击“准备真实地点”；也可以先创建空白会话，不必先调用模型。
2. 在城市目录中找“苏州”，查看完整城市和省份，明确确认。输入文字、展开卡片都不查高德。
3. 选择“必去地点”或“住宿参考点”，输入名称并点击“主动搜索高德地点”。这种方式不调用模型。
4. 也可以选“用一句话找”，例如“在苏州找拙政园作为必去”。明确提交后，模型最多选择一个工具；程序检查后最多进行一次逻辑搜索，不再追加模型总结。
5. 卡片列出真实搜索候选和地址。点击候选只是预览；核对名称、地址与城市后，点击“明确确认，加入必去”才写入本次地点准备。
6. 已确认地点按原顺序显示，可移除；必去最多6个，住宿只有一个。即使名称相同，也按POI ID区分。
7. 到这里暂停。没有生成路线、计算新费用、采用方案或保存行程；这些留在chat-3。

默认聊天仍用于整理需求，地点工具在按需展开的小卡中使用，不把旧工作台全部塞回首页。模型可能选错、地点可能有同名，不能只看到HTTP200或一个地址就宣称业务正确。

## 2. 全国与跨城分别是什么意思

| 用户表达／返回结果 | 应怎样处理 | 不能怎样处理 |
| --- | --- | --- |
| “去苏州” | 从可信目录确定城市，再在该城找真实地点 | 目录之外的文字静默回落到上海 |
| “想去西湖”但城市不明 | 询问是哪个城市／地点，让用户选择 | 默认取第一条或模型凭印象确认 |
| 上海搜索返回杭州同名POI | 拒绝这批错误归属结果，保留原确认地点 | 把搜索参数当归属证明、补城市字段 |
| “上海两天，再杭州三天” | 保留完整原话与跨城待澄清说明，不把合理需求当成非法输入 | 偷偷只处理上海，或者说跨城行程已安排 |
| 模型提出另一座城 | 先展示城市，等待用户明确切换，再主动搜索 | 模型自动切城、清空用户原工作 |

**拦的是错误数据和未经确认的执行，不是用户想跨城的意图。** 当前只保留多城原话和待澄清状态，尚无城市分段／多住宿数据模型，不把“继续询问”说成已经具备跨城规划。真正跨城还要处理城际交通、各城日期、换住宿和缓冲，另立阶段。

全国目录也不等于全国排程：新目录用于聊天城市选择与POI归属参考；旧`/legacy`、公交、天气、地图代理和saved-trip-v1/v2/v3仍保持原范围。六城外的地点不能直接塞进旧v3行程，更不能因为城市能选就承诺交通可用。

本轮目录基于可追溯官方表，包含369个大陆城市／自治州／部分省直辖单元，不把它们统称为369个地级市。港澳台及不能明确归组的条目不执行。获取日期、源版本、排除项和官方使用提醒见[目录说明](CHAT_CITY_CATALOG.md)；它不是当前行政区真实性认证，生产用途／更新方式仍需核对。

## 3. 按什么顺序实施

下面是chat-2内部步骤，不再建立一套与原计划冲突的阶段编号：

| 顺序 | 实际做什么 | 为什么先做它／怎样算完成 |
| --- | --- | --- |
| 准入 | 保留chat-1真实语义待验，先用受控输入开发；真实协议和额度另行冻结 | 不能把旧24条受控轨迹当模型成绩，也不借用历史额度 |
| 先建地基 | 定义工具与地点工作副本；在独立MySQL副本演练显式扩展 | 确认先有服务端依据，不能先写按钮再信客户端Place |
| 城市准备 | 独立全国目录、未知／歧义处理及旧城市ID兼容 | 只接受目录身份，不把旧存档的六城契约全局放宽 |
| 真实搜索 | 复用固定高德上游和发送处额度，保留真实归属及查询时间 | 无数据、归属异常、超时与额度拒绝分开，不造候选 |
| 预览确认 | 展示地址；用户按候选批次与ID确认、移除 | 服务端重查身份、城市、版本、去重和容量，事务提交 |
| 检查收尾 | 自动测试、受控浏览器、迁移演练与实际结果记录；真实验收单列 | 失败、待核、未执行保留，不能只以测试总数宣布质量通过 |

如果需求意向改了，地点副本先标过期，旧候选不能确认。用户明确同步时，同城可保留仍相关的确认地点；城市不同或无法确定则清除旧地点。单独修改地点准备城市不悄悄改需求卡，两边不一致时明确提示，chat-3合成正式输入前必须协调一致。

## 4. 工具不是“让模型想干什么就干什么”

| 能力 | 谁发起 | 数据来源／副作用 | 停止点 |
| --- | --- | --- | --- |
| 城市目录查询 | 用户选择城市 | 本地版本化目录，0模型／0高德 | 等用户确认城市 |
| `search_places` | 明确名称搜索，或一次原生`tool_calls`选择 | 一个已确认城市的固定高德搜索；结果写当前账号候选批次 | 展示候选，不自动确认 |
| `request_clarification` | 模型只能选有限原因 | 程序固定提示，保留原要求，不查询高德 | 等用户补充或确认城市 |
| 预览 | 用户点击 | 读取这份已保存候选，不新增查询 | 等用户核对 |
| 确认／移除 | **只能用户明确操作** | 服务端读取候选快照，更新本次地点工作副本 | 返回新版本，不生成行程 |

注册项要有名称、版本、输入输出、权限、读写性质、额度分类、超时、取消、返回上限及停止条件。首个Skill只是“找地点→预览→等待用户确认”的受控流程说明，不是能执行任意代码的插件平台。

自然语言路径使用真实`tools/tool_calls`，不是把普通JSON意图分类换个名字。无工具、多个工具、未知工具、坏JSON、额外参数或截断都结束本次操作，不猜着执行，不偷偷修补输出。确认接口不向模型开放，也不回送工具结果再调一次模型；这仍不是Agent loop、MCP或多Agent。

## 5. 为什么要有MySQL工作副本

浏览器显示的候选可能被改写，旧按钮可能过期，两个标签页也可能同时确认。所以服务端保存“当前用户、哪份对话、哪版需求、哪座城市、哪批搜索候选及已确认地点”；页面只引用它，不能提交一整份自称真实的Place。

```text
明确操作 → 登录／CSRF → 核对对话与版本 → 短事务登记操作
→ 如有必要，取额度后调用模型／高德（此时不持数据库锁）
→ 再核对版本并保存候选 → 用户预览 → 明确确认
→ 再核对批次、城市、去重与容量 → 短事务更新地点工作副本
```

`revision`就是递增的版本号。上海→杭州→上海虽然最终文字相同，也不是原来那次操作；旧成功、错误、finally和确认回调都不能复活。换号、取消、切会话、需求变化同样要失效。

新扩展`chat-places-storage-v1`使用两张表，与行程快照版本分开。只在空的独立目标复制迁移，保留账号、对话、旧存档、身份锚和全部额度尝试；运行时不自动建表、不切生产、不失败回退SQLite。确认结果不明时先读回执，同一操作不能换ID盲重发。重新读到地点不等于恢复了跨步骤任务，后者仍是chat-5。

显式迁移工具是[tools/chat_places_storage.py](../backend/tools/chat_places_storage.py)。仅查看帮助不会写库：

```sh
cd backend
.venv/bin/python -B -m tools.chat_places_storage --help
```

真正复制须先停所有写入者，准备空的独立目标；源由既有`TRIPPILOT_MYSQL_URL`配置，目标仅由服务端秘密配置`TRIPPILOT_CHAT_PLACES_COPY_TARGET_URL`提供，不把含密码URL放进命令或日志。再明确传`--receipt /absolute/private/new-receipt.json --anchor /absolute/private/existing-identity-anchor --confirm-source-stopped`。目标名限`trippilot_chat_`＋32位十六进制（测试另允许`trippilot_test_`）；不自动创建数据库或切换服务。

任何目标DDL前，复用现有备份校验逐行检查旧账号／会话／邀请／全部额度状态及v1-v3存档重放，再检查所有历史聊天收据和引用。复制提交后用**新的独立一致快照**比较源，不拿同一RR快照复读当“没有变化”。两次相等仍不能证明终检后无人再写，因此必须停写。提交后发现源变化时，目标可能已有ready标记，但收据失败；必须保留现场并禁止切换／盲重试，不能声称所有失败都回滚DDL。`--rollback-rehearsal`仅接受地点扩展两表全空，否则拒绝；不是丢弃用户已确认地点的回退方式。完整聊天／地点生产备份与恢复尚未完成。

## 6. 资源、失败与隐私边界

- 一次明确提交最多1次模型选择＋1次逻辑POI搜索；POI原连接失败最多重试1次，每次实际尝试分别计额。因此该路径最多3次实际上游尝试，不是3次模型调用。
- 模型仍非思考、非流式、1024输出Token、20秒单次截止；新地点操作共享45秒截止，前端等待50秒，既有同源代理75秒不变。取消后仍须等待已启动的数据库线程／任务清理，清理可能超过搜索截止，但不启动新上游。旧排程29条查询／58次尝试预算不增加。
- 关键词最多80字，问句最多2000字，接口完整解析前16KiB／5秒；候选最多20条，上游响应256KiB，前端响应384KiB。每会话最多100个地点操作收据，到限明确停止，不删除收据恢复额度。
- 同一副本不并发发送；失败、超时、已发取消及发送不确定保守占额，不自动重试。已观察到断开／取消不启动下一次上游；已发送不保证供应商停止处理或计费。
- 错误展示阶段与有限原因，不展示完整私密问题、原始模型正文、密钥或认证信息。工具日志仅必要ID、版本、分类、耗时和可取得用量，未知如实记未知。
- 密码、身份证、支付资料不要写进聊天；原话、模型提议、已确认地点分开，不升级成跨旅行长期偏好。知识库生成式问答继续停用。

## 7. 怎样验收，不靠“看起来挺智能”

开工前按类别固定开发／验证样本，题号、标签与标准答案不传给模型；本轮全部用受控上游，**不能报告真实地点搜索或模型识别正确率**。

| 类别 | 具体例子 | 程序／人工分别核对什么 |
| --- | --- | --- |
| 城市与归属 | 六城旧ID、苏州、特殊行政单元、未知城／同名／多城 | 目录与Python→TS一致；不串城，不猜默认城 |
| 原生工具协议 | 正确单工具、无工具、多工具、伪造确认工具／参数、注入 | 协议及权限严格拒绝；语义是否选对仍须真实评阅 |
| 地点确认 | 先预览、同名不同ID、重复ID、六必去上限、住宿兼作景点 | 只有明确确认才写；服务端取候选，不信客户端Place |
| 版本与取消 | A→B→A、切城、换号、取消、晚成功／错误／finally | 旧结果不提交，不复活旧按钮，不多发请求 |
| 额度和存储 | 并发、重启、ACK丢失、计数失败、空目标迁移 | 不返额／盲重发，原库不变，异常不永久busy |
| 页面与兼容 | 折叠、400px、键盘、旧六城排程／v1-v3读取 | 展示不发业务查询，不丢已确认地点，不破坏旧入口 |

错误身份／城市、未经确认写入、跨账号、旧状态污染、重复发送或数据丢失是阻塞，不能靠总分抵消。真实模型和高德验收要另行冻结版本、有限场景／次数和停止规则；模型错误原样留存，不无限换题找成功。

## 9. 面试时怎么讲

30～60秒：我没有让模型直接生成坐标或修改行程。模型最多选择一次受控搜索工具，地点身份来自真实搜索；服务端保存候选批次，用户预览后明确确认，提交时再检查账号、城市和版本。全国目录与旧六城排程分开，跨城需求会保留但不假装已执行。我们分别验证协议、最终写入和语义质量；离线通过不等于真实模型理解正确。

1. **为什么不能信模型返回的POI ID？** 模型提议不是供应商数据；确认必须引用服务端保存的候选批次和真实返回ID。
2. **注册表比函数列表多什么？** 它声明谁能调用、输入输出、读写后果、预算与停止条件，执行前还有程序校验，不是任意字符串找函数。
3. **为什么全国能选但不承诺全国排程？** 城市身份、POI、公交、天气和存档是不同契约／覆盖，后者尚未完成新范围验收。
4. **为什么跨城不直接拒绝？** 合理需求可以理解和保留，但不能把不具备的交通／多住宿能力包装成完成；错误POI归属仍要拦。
5. **为什么不立即做loop？** 先有可测的单步旅行工具基线；循环不能替代正确地点、权限和一致提交，chat-4再用同预算对照。
