# 聊天式旅行 Agent：分阶段重构计划

## 当前状态与使用方式

2026-10-20，核对基线 `fd1690c`，`main`。**本轮只定计划，未实施下列阶段，模型及外部业务API调用均为0，不操作服务器。** 工作区原有手工试用说明、五个Python缓存及浏览器日志保留。当前运行代码仍是旧工作台；登录注册及MySQL迁移能力已实现，但线上MySQL切换未执行。本文件不提供自动实施、迁移、部署或模型调用授权。

用户确认的产品是**旅行助手，不是通用聊天或客服产品**。默认交互彻底改为聊天，旧复杂工作台退出默认入口；不是把所有旧面板换个边框塞进聊天气泡。登录、注册、用户隔离、CSRF、额度、严格数据校验和真实数据链路保留。旧界面与业务代码逐项提取／退役，不删除用户数据、历史评分、证据和调用台账。

本文件统一维护新阶段编号与验收依赖；[AGENT_EVOLUTION](AGENT_EVOLUTION.md)保留架构原理、历史决策和教学约定，[ROADMAP](ROADMAP.md)维护更长期产品方向，[PROGRESS](PROGRESS.md)记录实际进度。下表全部是计划，不能作为简历中的已完成能力。

| 阶段 | 用户能够完成的事 | 关键交付／依赖 |
| --- | --- | --- |
| chat-1 | 用几轮对话说清旅行需求，查看并确认需求卡 | 聊天首页、多轮澄清、会话与需求版本、安全迁移 |
| chat-2 | 在对话中搜索并明确确认真实地点 | 工具／Skill注册、真实POI候选卡、服务端工作副本基础 |
| chat-3 | 在聊天里生成、核对、调整、采用并保存真实行程 | 确定性旅行闭环、权威工作区／费用边界；作为后续对照 |
| chat-4 | 让助手在有限步骤内完成有依赖的任务 | 简单／澄清／多步分流、有界单Agent loop |
| chat-5 | 暂停后安全继续任务，知道哪些步骤不能重跑 | 持久任务／步骤／尝试、恢复与幂等确认 |
| chat-6 | 自愿记住长期偏好；改善查资料时的相关性与缺口提示 | 偏好权限与冲突规则、检索分层评测，不恢复知识库问答 |
| chat-7 | 通过真实MCP接入一个受控的只读能力 | 独立协议适配、发现／调用／取消／权限测试 |
| chat-8 | 对有真实独立子任务的复杂旅行需求进行专业协作 | 协调者＋专业子Agent＋确定性校验，与单Agent对照 |
| chat-9（横向门槛） | 每个已验收的小版本可以稳定内测、演示和发布 | 按当次发布范围做退役审计与运维验证，不等待全部阶段 |

核心依赖为 **1→2→3→4→5**；chat-6依赖恢复／隐私边界，chat-8依赖稳定loop／恢复及实际专业工具，不要求先做完所有偏好或MCP。chat-7可在chat-2能力目录稳定且存在真实连接需求后单独安排。**chat-9是每个拟发布版本的横向门槛，不是全部1～8做完才发布**：chat-1可做限定需求确认内测，chat-3可做真实旅行闭环内测；长期偏好、MCP和多Agent不阻塞它们。评测、追踪、错误诊断、权限、成本和恢复设计从chat-1开始，不等到最后补。阶段过大时可分小提交，但不能靠只有界面或Mock结果宣称整阶段完成。

## 先固定产品和工程边界

### 交互与请求分流

- 默认只保留简洁会话导航、消息、输入和账号入口；需求、地点、行程、费用与预览按需展示紧凑结果卡。不要默认挂载旧控制器或自动触发旧查询。媒体、天气、地图等是否回归新交互，逐项验收，不承诺全部旧功能一次迁完。
- **简单操作**：明确日期查询／费用核对，走一个受控工具即可；不会为了“智能”制造循环。**信息不足**：先问缺什么，不猜日期、住宿或POI。**多步任务**：依赖具备后才进入chat-4执行器，逐步核对并在确认点暂停。
- 自然语言开放不代表执行范围无限：仍六城单选、1～7天、单住宿、6必去／本次3可选，不承诺最优或每天有活动。成都公交等真实历史限制保留。机票／酒店交易、跨城、多住宿及容量扩展不搭车实现。
- 用户原话、模型提议、用户确认是三种状态。模型提议的地点不是已确认Place；只读结果不是采用，采用不是保存，保存不是预订或付款。
- 新功能接入沿用服务端身份、Origin／CSRF和实际发送处持久额度；前端隐藏按钮不是权限。知识库生成式问答始终停用，计划不解除停用。

### 状态职责和迁移门槛

| 对象 | 规划中的职责 | 不代表什么 |
| --- | --- | --- |
| 登录会话 | 身份、过期、撤销、账号隔离 | 不是对话内容或任务状态 |
| conversation／message／turn | 用户与程序的会话记录、本轮请求身份、取消和发送收据 | 不接受客户端伪造system／tool历史；会话可读不等于任务已恢复 |
| requirements revision | 原话、待澄清／提议字段、确认的约束与真实POI；单调版本 | 模型推断不自动成为确认偏好或排程约束 |
| workspace revision | 权威候选、排除、设置、正式草案及相关费用版本 | 不是把React状态整体序列化入库 |
| task／step／tool attempt | 目标、执行进度、工具版本、发送前预记、结果与不确定状态 | 最终行程存档不等于断点；取消不保证上游停止计费 |
| preview／confirmation | 绑定输入和草案版本的拟变更、明确确认收据 | 不是任何Agent可自行提交的正式结果 |
| preference | 用户授权、来源、有效期、修改／删除和冲突处理 | 原始聊天和模型猜测不是永久事实 |
| saved-trip-v1/v2/v3 | 只读最终行程快照，原有版本与幂等含义保持 | 不是会话、工作副本或任务恢复库 |

当前正式草案、排除、费用和预览主要在前端Hook/ref；7A-1也是单次原生工具选择后由前端执行，**不是后端自主Agent**。chat-2/3需先建立服务端权威工作区及版本提交边界，前端展示其结果，不让两个独立状态源各自写正式草案。点击、模型返回、工具执行和采用前均复核身份／会话／需求／工作区版本，不能只比较内容或generated_at；A→B→A也必须隔离。

用户已选择MySQL，不另起数据库凑技术栈。当前`private-mysql-v1`严格检查表／列；新增会话与任务必须设计显式存储版本和迁移／回退，在空的独立测试库演练，不能偷偷运行create_all、放宽schema或改原库。新存储版本名称届时冻结，与saved-trip版本分开。生产MySQL切换及云端部署仍是独立操作，不由本计划执行。

当前整数分费用规则在`frontend/src/lib/schedule-costs.ts`。后端费用工具上线前，必须确定**一个权威计算边界**；若迁移／跨语言实现，先冻结规则版本并做Python→TypeScript差分契约与边界样本，避免长期维护两套漂移算法。未知／0／非法文本、多人票价、时间轴逐次交通计费均不得改变，也不信任客户端自报总价。

## 分阶段交付卡

### chat-1：聊天入口与真实多轮需求确认（下一步，尚未开始）

- **用户场景**：“想去杭州玩几天，带父母，别太赶。”助手问清日期、人数及必要约束；用户修改说法后看到最新需求卡，确认后形成结构化需求，而不是立刻编行程。
- **实现范围**：新默认聊天壳，保留注册登录；可新建／切换自己的会话、发送／取消。后端保存有界消息和结构化需求版本，模型负责有限澄清／提议，程序校验；未实现偏好只记录为待处理，不能声称已满足。此时确认的是需求意向版本，未核对的地点名称不能冒充合法Place或直接排程的TripRequest；chat-2补齐真实POI后再形成正式输入，不放宽原契约。先做离线UI／契约／迁移，再做经另行授权的真实多轮验证。只有前端气泡和固定回复不算完成。
- **请求控制**：每次主动提交最多一次模型请求，无自动重试或工具循环；新路径独立严格解析，沿用当前受支持Flash及北京配置，不改旧AI解析器。先复用现有单请求20秒／1024输出Token／有界输入输出等边界，新增路径必须进入额度发送分类、同源转发白名单和部署校验，不能只复用httpx就宣称计数覆盖。
- **一致性**：同一会话最多一个活动turn；短事务登记操作／版本，网络期间不持锁，结果以版本比较提交。已发送或提交结果不明的操作保留收据，不重复发送；完整任务恢复留到chat-5。退出／换号、改需求、取消与卸载隔离晚成功／错误／finally。定义会话保留及删除策略，不把完整对话写诊断日志。
- **开发体验**：独立测试身份／库、正常登录会话和可重复的受控测试入口；不增加生产万能密码、公开跳过登录或真实业务自动调用。
- **非目标**：本阶段不查真实路线、不生成假TripPlan、不自动搜索／保存，不引入MCP、多Agent或长期记忆。
- **验收／停止**：先冻结至少24条多轮受控轨迹，12开发／12冻结验证，覆盖完整信息、缺失、否定纠正、指代歧义、混合／越界请求、版本与账号隔离；保存失败与未实现约束。400px／键盘／取消、会话持久化和独立库迁移通过；真实模型小样本须后续明确授权，额度0时标待验，不假称完成。停止于“需求卡可确认”，不得自动进入工具执行。
- **讲解／面试追问**：为什么不能把聊天历史直接当需求？如何避免上一轮模型覆盖新输入？对话持久化与任务恢复差在哪里？用实际状态转换、版本冲突和失败轨迹作答。

### chat-2：能力注册与真实地点确认

- **用户场景**：用户提出想去的地点，程序搜索所选城市，展示地址与候选，用户明确选择住宿／必去；模型不能伪造ID、坐标或自动确认。
- **实现范围／依赖**：依赖chat-1；提取现有高德请求与严格归属校验，建立工具／Skill目录和服务端工作副本基础。首批仅启用有真实实现的POI搜索／候选预览／确认能力；尚无权威草案或费用时不能把日期／费用工具标为ready。
- **工具规范**：每项声明稳定名称、版本、输入／输出Schema、权限、只读／临时写／正式写类别、适用城市、额度单位、超时、取消、最大返回量、数据时效、幂等及验收样本。Skill是受控任务步骤和停止条件的组合，不是可任意执行代码的提示文件。动态任意URL、未注册工具、未知字段和跨账号ID均拒绝。
- **非目标**：不引入MCP假接口、不自动查询所有猜测、不顺便排程。地点确认不是模型工具结果或“同名命中”。
- **验收／停止**：未知工具／参数、跨城／缺归属、限额、超时、取消、相同名不同ID、容量／去重和旧确认回调；显示与展开不发请求；每次真实发送均计数，失败不变确认地点。停止于有效地点输入，不自动生成。
- **讲解／面试追问**：注册表比函数列表多什么？模型提议和用户确认权限如何区分？结构合法为什么不代表地点真实？

### chat-3：确定性真实旅行闭环（Agent对照基线）

- **用户场景**：确认需求与地点→主动生成→核对日期／费用→请求排除一个可选地点→查看预览→取消或采用→明确保存。
- **实现范围／依赖**：依赖chat-2。先把原有严格排程、版本提交、费用和存档边界接入聊天卡，完成权威工作区；主动候选准备、按ID排除／恢复及本次前三可选来源也在此迁移，不能凭空制造预览目标。复用现有算法和额度，不另写排程器。日期查询／费用核对可读当前正式状态；费用采用上一节的单一规则边界。需要时以结果卡展示地图／原因，不恢复全屏旧工作台。
- **确认与成本**：生成／搜索是明确的外部调用许可；拟排除不提前改正式状态。采用必须再次校验硬约束、依赖版本并原子提交，保存复用冻结内容和唯一操作ID。展示相关查询时间、未知、未安排及交通参考限制。
- **非目标**：这是确定性工作流，不叫自主Agent；不自动循环、采用、保存，不扩充城市／天数／排程优化，天气／媒体按需另议。
- **验收／停止**：真实数据与受控故障分开；取消保留原草案／费用，采用同步更新，旧保存成功不标记新草案；v1/v2/v3可读，新存档仍v3。费用与源规则差分、空日、部分安排、无路线、29查询／58尝试及截止守恒。停止于一条可演示、可测的完整旅行闭环，为chat-4提供同工具对照。
- **讲解／面试追问**：为什么先有工作流再loop？采用与保存为什么是不同提交？服务端权威状态如何避免前后端“双主”？

### chat-4：有界单Agent执行与复杂度分流

- **用户场景**：一句话要求“先看第二天与费用，再帮我预览去掉那个可选地点”，有依赖的任务可以有限推进，目标不明则先澄清，采用点等待用户。
- **实现范围／依赖**：依赖chat-3稳定工具和基线；真实原生tool_calls、工具结果反馈、显式状态机。只读简单任务单步，缺信息澄清，多步才进入loop。每轮校验工具参数、业务前提和版本；不展示模型自由编造的时间／费用。
- **有界条件**：实施前冻结总模型轮数、工具次数、Token、墙钟、实际外部尝试及任务额度；达到任一边界／重复无进展／版本改变／需确认即停止。工具内部原有路线预算不因外层loop扩大。没有授权不能开展真实调用比较。
- **非目标**：无限反思、失败自动修复、任意工具调用、跨账号写入、自动采用或支付。不得把一次JSON意图分类改名为loop。
- **验收／停止**：用相同工具、资料和总预算与chat-3基线比较完成率、澄清质量、错误调用、延迟和用量；覆盖单步、多步、无进展、取消、限额和部分失败。没有可解释收益不得强迫所有请求走loop。停止于有界执行与明确确认，不承诺掉线后继续。
- **讲解／面试追问**：何时不需要Agent？为什么多轮不等于死循环？外层工具次数为什么不能代替实际上游尝试计数？

### chat-5：持久任务、暂停与安全恢复

- **用户场景**：生成预览前暂停，换次登录继续；程序说明哪些依据已过期，重新确认后才继续或采用，不重复扣额。
- **实现范围／依赖**：依赖chat-4；持久task／step／attempt／checkpoint、操作ID、工具版本及最小结果引用，显式MySQL升级。恢复核对身份、需求／草案版本、数据时效、权限和剩余额度；旧预览不能因输入改回原值自动复活。
- **恢复语义**：发送前预记；未发、已发、已收、失败、取消、不确定严格区分。已发送结果不明不盲重跑、不返额；采用／保存的同操作重试复用已冻结内容与幂等键。短事务／竞争锁或租约具体方案届时实测，不能把网络调用包在长事务里。
- **非目标**：恢复过期票价／天气成“当前”；恢复旧会话令牌；承诺任意故障恰好一次外部执行。
- **验收／停止**：发送前后、持久化前后、采用／保存前后注入崩溃；双进程／双标签竞争、提交ACK丢失、重启、工具升级和账号撤销；无重复发送、旧状态采用或额度恢复。停止于限定任务可恢复，不扩长期偏好。
- **讲解／面试追问**：为什么存一份行程不够恢复？exactly-once为什么不能只靠重试？外部结果不明时用户看到什么？

### chat-6：经授权的偏好记忆与检索质量

- **用户场景**：用户主动允许记住常用偏好，下次可查看、纠正或撤回；查资料时知道资料相关性、时间和缺失，不能编造回答。
- **实现范围／依赖**：依赖chat-5状态和隐私边界；原话、模型推断、用户确认分层，显式当前要求优先于旧偏好；偏好来源／时间／适用条件可追踪。只有排程实际执行的约束才称满足，尚未支持者明确说明。资料问题区分语料缺失、分块、召回、排序、选材与时效，不一律换模型。
- **非目标**：聊天全文永久入向量库、默认记录敏感信息、把推断当事实；知识库生成式问答不恢复。向量库和Embedding若需引入须以词法检索对照及另行预算说明价值。
- **验收／停止**：拒绝记忆／授权／修改／删除／过期／跨账号与冲突；固定开发／验证集报告Hit@k、无资料误命中、馆区隔离及失败实例，旧成绩不改。停止于限定偏好和检索改进，不宣称通用长期记忆或RAG质量通过。
- **讲解／面试追问**：偏好为什么不是摘要？记住了“轻松”如何证明执行？召回不足和模型漏答如何分开定位？

### chat-7：真实MCP只读连接（可独立安排）

- **用户场景**：需要复用一个实际存在、受权限控制的只读能力，避免每个宿主单独接接口。
- **实现范围／依赖**：chat-2目录稳定且先确认具体业务工具与可信服务；采用真实MCP协议的能力发现、Schema、调用与错误／取消，不把REST代理改名。先只读白名单，桥接现有鉴权／额度／版本和传输边界；不允许模型配置任意服务地址。具体SDK／传输方式到实施时核对官方版本。
- **非目标**：为简历引入空MCP服务、远程执行代码或公开任意连接。MCP解决连接，不替代loop、业务校验或授权。
- **验收／停止**：真实本地协议交互与受控工具，未授权／未知工具／坏参数／超时／取消／版本变化，协议层不额外重试、每次实际发送可计数。停止于一个有用途的只读适配，不扩大工具权限。
- **讲解／面试追问**：协议与Agent运行时差在哪？为什么不能仅把HTTP接口叫MCP？服务发现后为什么仍要白名单与权限？

### chat-8：有真实收益的多Agent专业协作

- **用户场景**：行程、资料研究、预算等存在独立任务和不同证据来源，协调者分发、收集并解释冲突，而不是三个模型重复回答同一句话。
- **实现范围／依赖**：chat-4/5及相关业务工具验收；协调者＋有限专业子Agent＋确定性校验。共享同一需求版本、任务额度、截止和来源目录；子Agent提交建议，不得各自改正式草案。失败、取消、版本冲突和汇总职责明确。
- **机票／酒店门槛**：先核对真实供应、授权、价格时效、覆盖和费用。搜索研究／比较与预订／付款分阶段；没有数据不演示假航班或房价，没有交易授权不下单。酒店住宿参考点不是酒店服务。
- **非目标**：因为“旅行有多个领域”就认定必须多Agent；不加入第二评分模型或monitor模型作为默认成本。规则监测与trace先行，自动监控Agent需要独立效果／预算论证。
- **验收／停止**：同工具／数据／预算与单Agent对照质量、冲突、失败传播、延迟和成本；所有子任务失败也进分母，不能靠多数投票跳过硬约束。只有有收益的任务分支开放协作，未证明收益保留单Agent。停止于限定协作，不称自主预订旅行。
- **讲解／面试追问**：拆分依据是什么？多个Agent意见冲突谁说了算？并行是否值得增加费用和调试成本，用什么证据回答？

### chat-9：旧入口退役与受控发布（按版本触发的横向门槛）

- **用户场景**：登录后只看到清楚的聊天体验，自己的历史和任务可理解地访问，不因更新丢账号、存档或额度。
- **实现范围／依赖**：仅要求当次拟发布能力各自通过，不要求全部1～8完成。chat-1或chat-3即可各自准备限定内测，不等多Agent；是否实际发布仍需明确操作授权。建立旧UI／路由／控制器／契约／工具依赖清单，逐项提取或删除无依赖旧展示。历史报告与只读记录保留；旧/demo若继续维护须独立标识，不混入正式链路。工程治理与安全从前阶段已做，此处是每版门槛复核。
- **验收**：入口无旧控制器后台发请求，账号隔离／CSRF／限额／取消／幂等／恢复回归；迁移及回退、备份、日志脱敏、依赖、内存／磁盘与低配Linux验证，400px／键盘和端到端固定集。灰度、运行监控与数据删除流程具体冻结；代码回退不能恢复额度或旧会话。
- **非目标／停止**：不因本计划操作现有服务器，不承诺全部公开上线门槛已过；实际部署、生产迁移和新模型验收另授权。停止于可核验的受控发布版本，不顺延全国／媒体／交易扩展。
- **讲解／面试追问**：为什么保留旧证据而不保留旧工作台？代码回退与数据回退区别？如何知道新版本没有悄悄多调用？

## 每阶段统一验收与教学交付

1. **开工**：核对HEAD／工作区／服务／保护文件，写明本轮范围、状态和非目标。源码、参数、工具目录、题集、预期、预算与停止规则在真实发送前冻结；规划中的次数不是已授权额度。
2. **结果维度**：结构合法、工具选择、事实与约束、合法子问题覆盖、版本／权限、业务完成、成本／延迟／用户操作负担分别报告；检索、选择、渲染和执行错误不能混算。记录实际分子／分母、未执行和失败，不挑成功样本。
3. **阻塞门槛**：跨账号、无据事实、未确认正式写入、旧版本采用、重复发送／保存／扣额等均不能用总通过率抵消。结构化输出或引用存在也不证明业务正确。故障与执行异常停止条件按当轮协议执行，不临时补抽成功。
4. **证据分层**：单元／集成受控样本、历史回放、真实模型、真实业务上游、真实Chrome与服务器执行分别注明版本与边界；无模型额度时继续离线开发但真实验收待办，不把Mock当智能成功。保留旧失败与原台账。
5. **可观测性**：使用turn／task／step／attempt ID及必要版本、工具、状态、用量和耗时串起链路；未知用量记未知。不要存密码、Cookie、密钥、图片正文、完整私密提示或模型思维链。监控首批看失败分类、版本冲突、限额拒绝、延迟与不确定尝试，不宣称已具备大规模线上经验。
6. **讲明白**：每阶段报告写用户问题、实际代码／数据流、核心原理、取舍、一个真实失败／未验范围、运行与复现步骤、30～60秒口述和3～5个追问答案依据；上述阶段的3个问题是预习题，不是已完成答案。验收后才能写“我实现了”。
7. **收尾**：更新PROGRESS和专项记录，仅提交审查文件；保留五缓存、环境、用户数据、旧台账／评分／证据及无关修改。普通push，不强推，不自动开始下一阶段。
