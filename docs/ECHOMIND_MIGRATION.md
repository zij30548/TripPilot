# EchoMind 旅行领域迁移

更新：2026-10-22。开发基线 `19fb20c01a2fe0b210e9311e4049c6bff51fb312`。本次将用户提供的 EchoMind 作为架构参考，重组 TripPilot 后端并接入聊天工作区；不是将 EchoMind 原客服服务、依赖和数据直接覆盖本项目。

**当前验收口径**：自动检查／受控联调与固定真实复验分别记录。新增8次授权实际千问 **5/8**、高德 **2次POI＋2次步行物理发送**，其余外部业务调用0。首版api01失败保留；显式修复续验3个剩余用户请求通过，不拼成“4/4同版本通过”。旧聊天累计 **9/12、剩3暂停**及[旧失败](CHAT_ACCEPTANCE.md)不变。真实范围、版本变化及限制见第7.3节。

## 1. 解决什么问题

原聊天意向、地点副本和旧规划工作区分别存在，用户需要在不同入口操作。此次采用 EchoMind 的执行组织方式，让聊天后面有明确的角色路由、受控工具、结果反馈、停止原因和持久记录。真实地点、排程、交通、天气、费用、预览采用及存档仍由经过校验的程序处理。

用户可以从聊天开始，按需打开地点和规划卡片；确认地点、采用调整、保存记录仍是用户的明确操作。打开卡片不自动查询。聊天建议、工具事实、预览和正式结果分别展示，不能把模型文字当成已经执行。

当前仍是六城单选、1～7天、单住宿、6必去／本次3可选的旅行工具范围。聊天城市目录可表达更多目的地，目录存在不等于全国排程、天气和存档执行已开放。跨城需求先保留并澄清；成都完整公交的历史 `data_error` 未被此次迁移消除。知识库生成式问答继续停用。

## 2. 来源、采用和改造

参考源码为用户提供的 `EchoMind/`，版本 `ef847eb5b719ef98be9d5673f3429e62cd88109e`。该参考目录与本项目的交付代码分开；不把原项目的客服成绩、简历指标或完整能力描述归入 TripPilot。

选定来源文件哈希记录在[来源清单](../backend/evaluations/echomind-migration-sources.json)。上传版本未提供根LICENSE文件，本项目不据此声称原项目可任意再分发或全部为自己原创；面试、展示保留归属，进一步分发前仍须核对权利。这里是旅行领域的架构适配，不是把参考项目每个组件／成绩原样迁走。

| EchoMind 的设计 | TripPilot 的适配 | 保留的边界 |
| --- | --- | --- |
| 意图领域与角色路由 | 协调、地点、规划、预算角色；首版使用明确的词法路由，再由模型选择允许的原生工具 | 不是已校准的三路意图融合，也不称为并行专业多Agent |
| 原生工具执行与工具结果反馈 | 千问 `tools/tool_calls`；白名单参数校验，结果回送，再决定继续或等待用户 | 不把普通JSON意图提取称为Function Calling；没有任意Python／URL执行 |
| 有界Agent执行 | 一次任务共享模型次数、工具次数、Token和墙钟预算；重复无进展即停 | 角色切换不会获得新的完整额度；没有失败自动换模型或修复循环 |

| 分层记忆与状态 | MySQL中的账号会话、任务检查点、明确同意的偏好分别建模 | 不把对话存档说成无限记忆；模型推断不能直接写成长期偏好 |

| Evaluation | 确定性过程断言、最终业务状态核对及单独人工语义评审 | 默认不调用Judge模型，不以HTTP200或工具存在证明任务成功 |

没有原样引入 EchoMind 的 Anthropic SDK、Redis近期记忆、ChromaDB画像、本地Embedding、Docker、Prometheus服务组合。它们分别涉及协议、持久性、隐私、付费调用和部署资源；需要具体收益和独立验收才引入。现有约1.6GiB内存服务器事实来自用户终端记录，本轮没有登录服务器或验证新架构的生产容量。

## 3. 后端组织和实际分工

迁移后的组织如下。原 `app/` 业务模块按职责移动、修改导入，不复制第二套排程或计费算法；原五个受保护Python缓存留在原位置，不成为运行模块或交付文件。

```text
backend/
  main.py                 FastAPI启动入口
  api/                    身份、聊天、地点、排程、媒体、存档等HTTP边界
  agents/                 协调器、角色、工具声明和有界执行
  core/                   配置、身份、额度、执行上下文、意图及Skill加载
    schemas/              严格请求、响应、快照和模型结构
  tooling/
    providers/            千问、高德等固定上游与协议适配
    travel/               地点、规则排程、交通、天气及解释等领域逻辑
  memory/                 会话、任务检查点、偏好及持久化
  monitor/                脱敏执行观察
  evaluation/             无付费调用的过程／结果评测
  skills/                 受信任的本地旅行规则
  tools/                  显式初始化、复制迁移、备份和验收CLI
  tests/                  隔离数据、受控模型／上游与契约回归
```

前端继续使用 Next.js／TypeScript、同源请求、身份epoch与AbortController。聊天主入口按需展示已有地点卡片及 `EditablePlanningSession → PlanningWorkspace`，复用原时间轴、地图、费用、预览采用和存档能力，不把整份React状态当任务存储格式。正式规划仍由前端本地控制器管理，刷新会丢失未明确保存的草案／估算；任务收据存在不等于整份行程可以从服务端恢复。

当前 `get_day_schedule`／`get_budget_summary` 提供的是程序面板导航，后端没有接收整份本地正式草案和费用输入，不能把这两个工具描述成已经返回当前日期／费用的服务端事实结果。查看实际时间轴和费用仍须打开相应程序卡片。普通模型文本统一视作尚需核实的建议；页面固定说明“对话建议尚需核实；真实地点、时间和费用以你确认后的程序卡片为准。”

核心数据流：

```text
用户主动发送
  → Cookie身份／Origin／CSRF／会话版本
  → MySQL登记本次操作与任务
  → 角色和受信任Skill／工具白名单
  → 千问原生工具选择
  → 参数、账号、版本、持久额度及资源校验
  → 确定性旅行工具
  → 工具结果反馈／等待确认／预算停止
  → 校验并持久记录
  → 聊天与按需卡片展示
```

## 4. 有界执行与事实权限

当前运行时预算设计为每任务最多3次模型请求、4次工具执行、45秒总执行；每次模型最多2048输出Token，全任务最多6144，仍受每账号／全局持久额度约束。单次上游请求保持原有20秒整次截止、输入和响应大小限制。缺失用量按本次保留的输出预算核算，不据此产生新余额。最终有效值及实际测试以本轮代码和验证表为准。

每轮只接受一个允许工具；未知工具、多个调用、坏参数、截断、重复调用ID和重复无进展输入明确停止。工具结果可以反馈给模型，但每次反馈后的请求都重新计入共享任务预算和持久发送次数；不自动重试。原行程解读／调整等独立接口的校验不会因为新工具路径而放宽。

角色是协调器内的职责分流，不表示多个专业Agent正在并行研究并各自提交行程。模型可以选择工具或提出建议，真实POI、交通分钟、票价、日期、费用计算及未安排原因由程序／上游结果提供。工具操作仍区分只读、创建预览和正式提交；模型选择不能绕过地点确认、采用和保存入口。

## 5. 状态、偏好和恢复语义

新扩展标记为 `assistant-storage-v1`，独立于聊天、地点和 `saved-trip-v1/v2/v3`。

| 数据 | 职责 |
| --- | --- |
| 账号／会话 | 既有MySQL身份、密码哈希、Cookie会话、CSRF与归属；不接受客户端owner_id |
| 聊天与地点副本 | 原文、需求提议、确认版本、候选批次与用户已确认POI；保留原版本边界 |
| `assistant_tasks` | 操作ID、账号／会话、绑定的会话版本、独立CAS revision、顺序号、状态及有界检查点 |
| `assistant_preferences` | 用户明确同意的偏好原文、来源、版本与时间；支持修改／撤回 |
| 原行程存档 | 用户明确保存的正式快照，保留v1～v3严格含义，不变成任务检查点 |

任务状态为 `running/waiting/succeeded/failed/cancelled/uncertain`。同一操作ID使用后不能因失败、取消、重启或切换目录而重新发送。任务检查点最大2MiB；Trace只留有界白名单元数据。正式工具结果需先过领域契约；容量超限明确失败，不截断成“完整结果”。

`checkpoint`必须核对任务版本和当前会话版本。聊天完成会使会话版本递增，`finalize`还要核对最新聊天轮的操作ID、冻结版本和完成状态，才允许绑定到完成后的版本。查到任务不等于可以继续执行；恢复先检查数据时效、归属、版本及真实结果。运行中或发送结果不确定时，只读回记录，不自动重放。新请求或用户明确操作仍须取得新操作ID和本次额度。

偏好只接受 `source=user` 和明确 `consent=true`。用户撤回后清除文本，保留递增版本墓碑，避免删除再创建把旧回调变成有效操作。当前旅行要求优先于长期偏好；没有实现的旅行约束不能因偏好已经保存而声称排程已满足。

## 6. 显式复制迁移与运行边界

新能力不在启动时建表、迁移、复制或切库。未准备assistant扩展时明确报 `assistant_migration_required`，MySQL故障不回退SQLite。测试中注入的临时SQLite仅用于兼容／事务行为检查，不是新运行后端选型。

新工具为 `backend/tools/assistant_storage.py`，支持从已停写的MySQL源复制到**新的空隔离目标**，增加assistant扩展；源已有assistant记录时也完整复制。它保留账号ID、会话、邀请、旧v1～v3存档、聊天、地点及全部额度attempt状态，使用原额度身份锚，不返额。先校验源内容、引用、版本和上限，再开始目标DDL；MySQL DDL不能假称事务回滚。

操作员在独立迁移环境配置私有 `TRIPPILOT_ASSISTANT_COPY_TARGET_URL`，目标只允许受控随机测试／演练库名。配置和原锚不写入命令参数或公开报告。以下是工具说明，不是已经执行生产迁移：

```sh
cd backend
.venv/bin/python -B -m tools.assistant_storage \
  --receipt /absolute/private/NEW-receipt.json \
  --anchor /absolute/private/ORIGINAL-usage.identity \
  --confirm-source-stopped
```

预期成功收据包含 `state=verified`、`quota_refunded=false`、原锚哈希及各表行数／摘要。Receipt独占创建、权限0600；目标非空、Receipt已存在、源损坏、锚不符、锁占用或复制不确定均停止并保留现场。复制后另取源快照核对，但两份快照相同不能证明未来没有写入，仍要求操作员先停全部写入者。

旧复制和备份入口不支持assistant格式时明确拒绝，不能生成遗漏新表的“完整备份”。源库、旧库及旧数据文件保持不变；此一致性复制不等于已建立完整生产灾难恢复平台。现有线上服务不因git push自动更新；新发布目录、最终路径验证、数据准入、备份／恢复及服务切换需要另行按 [RELEASE_1F](RELEASE_1F.md)、[MYSQL_REGISTRATION](MYSQL_REGISTRATION.md) 核对。

### 7.2 已发现的真实UI故障及补修

首轮受控Chrome发现地点区域重复挂载、标签关联重复和连续GET。根因是同层 `ChatPlaces` 与 `AssistantPreferences` 都使用会话ID作key；子组件 `onWorkspace` 更新父状态后触发错误复用。修复为 `places:${id}`／`preferences:${id}` 独立key，并补真正的 `Home + ChatPlaces` 组合测试，执行其真实effect及父级回传，而非mock掉组件回调：重渲染与需求卡切换后，两区域各一份、地点GET一次，无自动模型或偏好请求。
