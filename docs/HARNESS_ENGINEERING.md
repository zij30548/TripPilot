# TripPilot Harness 工程约定

更新：2026-10-21；核对基线`3c2877593df25c5b67b4c0e7d6673bafaa6eee3c`。用户要求后续开发遵循完整Harness原则。本文件把要求落实为**覆盖清单、代码依据、阶段准入和失败反馈**，不新增业务功能、模型调用额度、Agent loop或部署授权。

“齐全”指每阶段都审视完整工程维度，不是立即实现全部能力，更不是写完文档便宣称全部通过。本文12项是**TripPilot的项目约定**，不是某篇文章原封不动的“行业统一12原则”。若用户后续指定某份原则清单，另作逐条映射、保留差异，不冒称已按未知标准认证。

## 一、先分清三种Harness

| 层次 | 在本项目解决什么 | 不能混淆的边界 |
| --- | --- | --- |
| 开发Harness | 让维护者／Codex从仓库恢复事实、获得可运行环境，小步修改并取得可核验证据 | Codex使用子Agent、浏览器或技能，不代表TripPilot产品已经有这些能力 |
| 产品运行Harness | 围绕模型的上下文、状态、工具权限、额度、取消、确认、执行与恢复机制 | 不是只写system prompt；一次结构化意向整理不等于自主loop |
| 评测Harness | 固定输入／版本／预期、持久计数、受控故障、逐项评分及失败留存 | 测试工具通过不等于模型语义正确；模型输出通过不等于最终业务状态正确 |

这三层互相提供反馈，但不能互相代替。以下要求同时覆盖开发过程与产品演进，具体交付阶段仍只有[CHAT_REBUILD_PLAN](CHAT_REBUILD_PLAN.md)中的chat-1～chat-9，不新增一条并行实施主线。

状态口径：**已有基础**表示存在可核对代码／历史证据，不是全量验收；**部分**表示缺少整体能力或当前版本效果证据；**规划**表示尚未实施。未来要求不因写入本表就获得实现授权。

| ID／原则 | 必须落实的工程约束 | 当前依据与缺口 | 对应准入／验收 |
| --- | --- | --- | --- |
| H01 目标、范围与完成定义 | 先写用户场景、非目标、前提、成功／失败及停止点；人决定产品方向，程序检查业务结果，不让模型口头宣布完成 | 已有阶段计划、PROGRESS和冻结评测；chat-1只到需求意向确认 | 每阶段交付卡写清状态；未确认POI不能称行程输入已完成，未发布不能称线上已更新 |

| H06 分层记忆与隐私 | 工作记忆、会话、任务与长期偏好分开；仅用户授权的偏好可跨旅行复用，可查看、修正、撤回／删除并有来源和适用范围 | 对话／本次意向可持久；[chat契约](../backend/app/schemas/chat.py)中的preferences不是长期画像。长期偏好服务仍规划 | chat-6测试同意／拒绝／过期／删除／冲突／换号；用户本次要求优先，模型推断不能自动写成已确认偏好 |
| H07 检查点、幂等与不确定恢复 | task／step／attempt／checkpoint分别有职责；未发、已发、已收、失败、取消、结果未知分开；恢复先核对时效／版本／权限 | ChatStore／[额度发送边界](../backend/app/usage_runtime.py)保留操作和尝试；不是完整任务恢复。已用操作不重发，最终存档不是检查点 | chat-5需重启、双进程、ACK丢失、发送前后／提交前后故障；不承诺外部exactly-once，不因未知重跑或返额 |
| H08 安全隔离与明确人工确认 | 服务端身份、CSRF、账号归属、固定上游、上传／解码边界；把用户／网页／图片指令当不可信数据；正式采用／保存由用户确认 | [身份门禁](../backend/app/auth.py)、[部署配置边界](RELEASE_1F.md)及媒体约束已有；[本机自动普通登录](CHAT_1.md#2026-10-21本机测试暂时免填登录不删除功能)不关闭鉴权 | 未授权0外部发送，跨账号／跨城／伪造引用／注入为阻塞；测试便利不能变成生产免登录或万能密码 |
| H09 持久额度与资源边界 | 发送前原子取额，账号与全局限制，失败／已发取消／不确定不随意退额；同时限制上传、并发、时间、输出和循环；不把次数等同人民币 | [MySQL额度](../backend/app/mysql_usage.py)、[业务边界](../backend/app/business_usage.py)和媒体容量已有；任务级聚合预算、供应商账单核对仍有缺口 | loop／子Agent共享同一任务预算，不能每个子任务获得完整新额度；重启不补额，计数故障失败关闭；真实验收额度单独授权 |
| H10 可观测、可诊断且脱敏 | 用稳定的conversation／turn／task／step／attempt和版本串起链路；记录必要结果类、耗时、请求模型、实际用量／未知、停止原因；错误定位到阶段 | [chat API](../backend/app/api/chat.py)与旧诊断／额度有局部记录；全链路统一trace、生产指标看板／告警尚未建成 | 区分意图、资料覆盖、召回、选材、校验、权限、上游、提交和展示失败；不存密码、会话值、照片正文、私密完整提示或模型思维链；monitor不默认再调一个模型 |
| H11 结果导向的评测与真实证据 | 过程和最终业务状态分别评；冻结开发／验证集、版本、预期、预算与停止条件，保留失败；先确定性断言，再做必要人工语义核对 | [24条chat轨迹](../backend/evaluations/chat1-trajectories-v1.json)与[测试](../backend/tests/test_chat_trajectories.py)是离线预期／受控回放；chat-1真实语义仍待验。旧知识问答失败和停用保持 | 结构、语义、工具选材、事实／条件、约束、账号／版本、任务完成、延迟／用量分开报告；不能拿HTTP200、截图、断言总数或引用存在替代业务质量 |
| H12 可维护架构、运行环境与反馈闭环 | 清晰分层、单一规则、可重复启动／检查、显式数据迁移、备份／回退、依赖安全和文档导航；失败沉淀为回归而非只追加提示 | 现有测试／严格契约／部署工具提供部分机械约束；未有覆盖全部分层／文档漂移的统一CI门禁；新聊天生产备份／恢复仍未准入 | 每轮修一个明确问题、补对应测试／证据；定期识别重复实现、失效说明和临时代码，单独审查再收敛，不自动清理数据／历史证据；发布不以合并代码替代验收 |

**不通过总分豁免阻塞**：跨账号、无依据事实／身份、未经确认写入、错误版本采用、重复发送／返额、数据丢失或不确定写入被宣称成功，均必须单独阻断相应能力的验收。文档覆盖12项不意味着代码12/12达标，也不制作没有实际评测依据的“Harness成熟度百分比”。

## 三、开发Harness的固定工作流

1. **恢复事实**：按根AGENTS依次读取README、PROJECT_CONTEXT、ROADMAP、PROGRESS，再按任务进入本文件／阶段报告／局部指令。核对HEAD、分支、脏工作区、原服务和受保护文件。对话不是唯一需求账本；旧记录保留时间与当时状态。
2. **只选一个获授权闭环**：列目标／非目标、依赖、精确完成标准和风险。小修写短计划，复杂任务使用现有阶段文档；不为遵循Harness就把所有阶段、工具或框架一次实现。
3. **准备受控环境**：独立测试身份／临时库，密钥仅服务端；复用已有服务需先核对。先离线验证，不拿付费调用排连通性，不操作生产来代替演练。手工测试入口只建立正常会话，不免除服务端鉴权。
4. **小步实现并机械校验边界**：复用严格Schema／权威规则；补成功、失败、取消／旧响应、权限、额度及不确定状态测试。反复出现的同类问题应提炼共享约束或结构测试，不能只在提示中再说一遍“不要错”。本轮仅建立规范，没有新增这些自动检查器。
5. **按影响面验证**：业务源码跑相关测试／必要回归；前端变更按AGENTS检查；纯文档只核链接、事实、命令、敏感信息和diff。Chrome、真实模型、真实上游和Linux服务器分别给证据，不互相冒充。没有调用授权就留待验，不无限重试找成功。
6. **交接与收尾**：阶段报告记录问题、机制、取舍、代码、实际命令／版本／结果、失败／限制、下一停止点及面试说明；PROGRESS顶部保留简明当前导航，旧历史不重写。仅暂存已审查文件，普通提交／推送，不将代码同步写成部署完成。

资料应分层可发现，AGENTS只放入口和不可违反的约束，细节放专题文档；PROGRESS保留历史但顶部清楚，避免把越来越长的聊天／指令一次全部塞入模型。历史清理、文件拆分或自动巡检须另有范围，不由本约定自动启动。

## 五、缺口按原阶段补，不另堆技术栈

- **当前chat-1待验**：24轨迹不是模型通过率；下一轮先定义真实语义协议并另获额度。生产新聊天数据备份／恢复门槛仍待补。当前本机自动普通登录只便利测试，不改变这个结论。
- **chat-2/3**：统一工具／Skill目录、真实POI确认、服务端权威旅行工作副本与单一费用规则；先建立确定性完整闭环，不能直接把原前端工具当后端Agent。
- **chat-4/5**：原生工具调用与结果反馈、有界loop、跨步骤预算、无进展停止；再做持久任务与故障恢复。未知已发不盲重跑是从现在就必须保留的安全要求，不等chat-5才考虑。
- **chat-6/7/8**：经授权长期偏好与检索质量、真实有用的MCP、相同数据／工具／预算下有证据收益的专业协作。多Agent不是“齐全”的前置，也不能各自提交正式方案。机票／酒店真实数据和交易权限另行确定。
- **chat-9及每版横向门槛**：权限、额度、迁移、备份、低配Linux运行、依赖、可观测与受控发布从每轮检查，不等到全部Agent做完才考虑。LangGraph、Redis、向量库、监控平台等只为具体缺口另行选型；当前私有存储可显式使用MySQL，SQLite旧兼容不是新运行链路混用，更不自动授权清库或生产迁移。

知识库生成式问答继续停用；旧失败、媒体识别限制、成都公交data_error、历史评分及所有已耗尽调用台账不变。当前没有新的真实模型调用授权。Harness是把失败变成可诊断、可约束、可验证的工程闭环，不是保证模型不犯错。

**30～60秒口述**：我把Harness理解为模型之外的工程控制，不只是提示词。项目分别约束开发过程、产品运行和效果评测：开发靠仓库事实与小步验证，运行靠严格契约、账号与版本、持久额度和明确确认，评测核对最终业务状态并保留失败。目前已做聊天意向及这些局部保护，真实语义还待验；有界loop、完整任务恢复和长期偏好按阶段建设，不能提前写成已实现。

**项目追问**：

1. **Harness和prompt差在哪？** 引用chat API／storage／usage_runtime说明：提示无法单独完成权限、原子取额、持久版本和取消隔离。
2. **有Schema为什么还要评测？** Schema管结构，原文引用管出处；否定理解、工具选材、约束是否满足及最终写入仍需独立判定。chat-1真实语义尚待验证。
3. **聊天存MySQL为什么不等于恢复？** 能读取消息和turn收据，不代表有task／step／checkpoint，也不能证明未知外部调用没有执行。
4. **为什么不先引入完整框架／多Agent？** 先有受控旅行工具和单流程基线，收益、成本与复杂度有对照再增加；框架名字不解决错误数据或正式提交一致性。
5. **怎样证明这些不是文档口号？** 每轮交付卡连到代码、实际检查和失败；反复错误提炼为机械约束。当前只有部分代码检查，统一架构／文档CI门禁未实现，不会说已全自动覆盖。

本轮停止在规范和导航同步，不修改业务、数据库、服务、模型配置、提示或评测标准，不启动上述缺口的实现。
