# 旅行能力接入纯聊天：实现、边界与验证

更新：2026-10-22。本文描述本轮 `dialogue-v2` 接入，不改写 [EchoMind 迁移](ECHOMIND_MIGRATION.md)、[旧 chat 验收](CHAT_ACCEPTANCE.md)或媒体的历史成绩。交付状态和最终全量检查以 [PROGRESS](PROGRESS.md) 本轮记录为准。

## 1. 用户问题与这次解决的范围

用户不希望重新使用旅行卡片，也不希望助手只说“去下方查看”。这次把已经存在的地点、规划、费用、预览、天气、存档等操作，接入同一个消息区：用户提出要求，程序显示实际结果，需要修改或产生外部调用时再明确确认。地图、文件选择和完整需求编辑只在主动操作后临时打开；主导航仍是聊天、资料检索和执行核查三页。

这不是“任何旅游问题都能答对”。没有来源的票价、营业、预约、实时余量，不能靠语言流畅度补出来。知识库仍只检索已收录的上海三个馆区，不恢复生成式问答。全国目录不等于全国排程；正式工具继续六城、单城、1～7 天、单住宿、6 必去／本次 3 可选。

本轮实际模型、高德及其他真实外部业务调用为 **0**。旧额度不借用。实现和受控测试不是本版真实模型理解质量验收。

## 2. 数据流：选择动作与提供事实分开

1. 少数明确命令直接进入程序，例如“查看行程”“核对费用”“预览地点 1”；不为这些操作额外调用模型。
2. 其余自然语言通过现有 `/chat/conversations/{id}/assistant-turns`，附 `X-TripPilot-Surface: dialogue-v2`。身份、CSRF、操作预记、输入长度和业务额度沿用原边界。
3. 模型只选择严格的原生工具。38 个动作合并为 10 个有限工具组；另有需求读取、需求整理、澄清和固定一般建议。每个 v2 工具都是终止步骤，不自动继续规划或回调第二次模型总结。
4. 后端校验工具组、动作、参数及当前任务。程序生成“待核对请求”的文本，不接受模型自由编写的交通、金额、营业等事实正文。
5. 前端通过只读 `/chat/conversations/{id}/dialogue-action` 读取唯一当前提议，逐项比较账号、会话、revision、operation_id 和本地工作区代际。这个接口只投影明确白名单，不开放任意任务检查点。
6. 前端在真正执行时再次核对状态。需要确认时，先展示对象及操作，等待“确认”；旧确认、双击、取消后的回调不能提交。通过后复用现有控制器及严格请求，程序把其真实结果转成消息。

共享注册表：[dialogue-actions.json](../shared/dialogue-actions.json)。后端契约：[dialogue.py](../backend/core/schemas/dialogue.py)；工具：[travel/dialogue.py](../backend/tooling/travel/dialogue.py)；接口：[assistant.py](../backend/api/assistant.py)。前端：[dialogue-action.ts](../frontend/src/lib/dialogue-action.ts)、[dialogue-tools.tsx](../frontend/src/components/chat/dialogue-tools.tsx)。没有维护第二套排程器或计费器。

无 header 的旧调用和 `dialogue-v1` 保留原能力与严格请求语义。v2 的选择上下文不会令旧接口接受任意新字段，也没有放宽原行程 AI、照片、存档或知识问答契约。

**提示适配的实际核对**：现有三份旅行 Skill 是通用安全规则，并未发现正文含过期工具名，不能把这种风险写成已复现根因。实际差异是旧通用运行提示要求“读取工具结果后再决定下一步”，而 v2 是终止提议。v2 因此使用单独的静态终止提议规则，等价保留原三份 Skill 的数据不可信、POI／城市／照片身份、确认、未知费用及范围边界；只列当前角色过滤后真正注册的函数名，不注入旧 Skill 自由正文。没有 header／v1 仍使用原 `SYSTEM + Skill` 反馈路径。界面列出的 Skill 是已加载目录，不等于 v2 将其全部正文注入模型。

## 3. 38 项能力与确认边界

“确认”指程序展示待操作对象后，由用户明确确认；不是模型在工具参数中写 `true`。表中的“不需要”也不代表不校验账号、版本或目标。“打开”媒体只是文件入口，选择文件不自动上传、识别或搜索。

## 4. 状态、上下文与持久化边界

### 谁持有权威状态

- 服务端：账号／会话、对话、结构化意向、真实地点批次与明确确认、任务收据、同意保存的长期偏好、存档和额度。
- 当前浏览器：正式草案、停留／午餐设置、可选候选、原始费用估算、天气检查、调整预览、地图和临时媒体。这些通过既有控制器持有，不直接序列化成任务检查点。
- 当前对话提议：只是一项有版本的操作请求。没有正式草案时，费用／日程读取明确说明缺少前提，不从任务任意 JSON 或旧 Mock 推断事实。

刷新、切换账号／会话可能丢失未保存的规划与本地消息结果。本轮没有实现完整服务端规划恢复。历史副本和完整需求编辑可能只改变本地规划输入，不能把聊天意向伪装成已同步；页面消息明确说明这一边界。最终行程存档也不是整个 Agent 执行过程的断点。

### 跨轮选择上下文

v2 可以携带 `dialogue_context`：UUID4 工作区 token、显示类别，以及最多 20 项 `{ordinal,id,name,type}` 标签。字段、长度、枚举、重复编号均严格校验；不带坐标、金额、完整结果或任意业务对象。它进入 `untrusted_dialogue_selection`，仅帮助理解“第二个”“刚才那个名称”，不是服务端事实、地点认证、权限或执行证据。

标签内指令不可信；程序执行时仍从当前本地结果按唯一 ID／名称／可见编号解析，歧义时停止。模型选择正确性仍需语义评测，不能由这个 Schema 证明。完整费用和路线没有自动回送给模型，复杂的多轮比较仍可能需要用户明确对象；本轮不宣称任意上下文都能理解。

最终交叉审查补了两个提交边界：自然语言的数字选择先按**发问时冻结的显示列表**解析成 ID，再进入领域控制器，不能把时间轴第一个必去重新解释成可选集合的第一个地点。找不到、类型不符或不唯一时拒绝，必去仍不能排除。保存处于 `saving/uncertain` 时，禁止重新准备、编辑确认、窗口重建或历史恢复卸载原控制器；必须先按原冻结快照／操作 ID 核对保存。相同账号即使已经修改聊天需求，也只能重试那份旧快照，不能借此保存当前失效草案。刷新／切换会话仍没有完整持久执行恢复，不能声称这一护栏解决了所有断点。

### 本轮发现并处理的候选连续性问题

旧逻辑每完成一个模型轮就同步地点并清空候选，因此“搜索→自然语言预览第一项→自然语言确认”会丢失刚才的列表。v2 增加**内部**连续性证明：捕获原批次 ID／内容哈希、原地点版本、需求版本、城市及需求哈希；只有原批次仍是当前持久内容、没有并发操作、实际需求完全不变且恰经过当前一轮，才把同一批次绑定到新 revision。

这不是恢复旧搜索：需求变化、城市 A→B→A、新搜索、旧版本或不确定操作均不得承接。原查询时间和地点内容不刷新；旧确认 token 仍失效，必须在新版本重新预览。没有 header／v1／普通显式 sync 仍按旧规则清空批次。实现见 [chat_places_storage.py](../backend/memory/chat_places_storage.py)，没有数据库表或存档版本变化。

## 5. 事实安全不能只靠一句免责声明

- v2 如果模型返回自由正文而没有允许的工具，明确结束为 `ungrounded_answer`，不会在正文前加“请核实”后照常展示。
- 日程、地点、费用、天气、预览与历史都由程序展示当前有效结果；模型不能自由填入 POI ID、价格或路线时间。
- 老人、亲子、行李、节奏等一般建议是有限的程序文本，不会承诺营业、票价或个体适用性。无法确认的实时事项明确说不能确认。
- 选择无关的一条固定建议仍然可能“安全但没答到问题”。合法工具／正确引用／HTTP 200 只证明部分技术边界，不能等同回复有用或完整。
- 资料检索保留摘要与短摘录的区别、官方链接、来源／获取时间及适用性；不会恢复 `/knowledge/answer`。

## 8. 口头说明与面试追问

可以这样解释：“这次不是让模型生成一段看起来像行程的文字，而是让它在有限工具中选择。程序核验当前会话和工作区，用户确认后执行已有真实能力，再把真实结果放回聊天。事实来源、状态提交和模型选材分别验收；我修复过自然语言下一轮清掉候选的真实接线问题，用原批次及版本证明承接，而不是关闭校验。”

可用代码和测试回答的追问：

1. **为什么不让模型直接写价格和时间？** 正式数据在现有排程／费用控制器，自由文字没有来源保证；v2 拒绝非工具正文。
2. **如何防止“确认”提交旧操作？** 确认 token 绑定账号 epoch、会话 revision、操作和工作区代际，消费后不能复用，业务提交还有自身 CAS。
3. **自然语言“第一个”怎么跨轮保留？** 有界显示标签辅助选择；服务端仅对实际需求不变且原批次仍当前的本轮承接，重新预览后才允许确认。
4. **Schema 合法为什么不等于答对？** 能选到合法但无关工具；测试明确保留这种语义缺口，真实评测另看相关性、完整性和业务结果。
5. **现在是不是完整持久 Agent loop？** 不是。旧 runtime 有有限反馈能力，v2 操作选择是终止提议；正式规划仍在浏览器，任务收据不等于完整恢复。

停止在本轮接入与已记录的验证范围，不自动开启知识生成问答、并行专业 Agent、云端迁移或新的真实验收。
